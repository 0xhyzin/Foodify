# إصلاح فتح بوابة Paymob

هذا سجل التشخيص اليدوي السابق. أُضيفت بعده اختبارات آلية للبوابة والعقود ومسارات الدفع في مراجعة 2026-11-03؛ نتائجها الحالية وحدودها في [سجل التحقق](SPRINT_2_VERIFICATION.md). وصف عدم تشغيل tests أدناه يخص جلسة التشخيص الأصلية فقط.

## المشكلة التي تمت مراجعتها

كانت الواجهة تنتظر إنشاء جلسة الدفع ثم تنتقل إلى Paymob. إذا رفض المزود تجهيز الجلسة، كان الباك يعامل الرفض الصريح مثل انقطاع الاتصال، ويضع الدفع في `initialization_unknown`. في هذه الحالة يُمنع إنشاء جلسة ثانية لحماية العميل من تكرار الدفع، لكن السبب لم يكن واضحًا في السجلات.

الفحص المحلي وجد طلبين قديمين بهذه الحالة، دون `intention_id` أو رابط دفع محفوظ. لم نعد إرسالهما ولم نغيّر حالتهما؛ غياب هذه القيم محليًا لا يثبت وحده أن المزود لم ينشئ جلسة سابقًا.

## التعديلات

- رابط الدفع الجديد يستخدم `https://eg.checkout.paymob.com/` مباشرة، وهو العنوان الحالي في أمثلة Paymob الرسمية. العنوان القديم كان يمر أولًا على تحويل إلى هذا النطاق.
- يتحقق الفرونت من HTTPS والنطاق والمسار المحددين، ووجود `publicKey` و`clientSecret` مرة واحدة لكل منهما، وصلاحية وقت انتهاء الرابط. ويقبل المسار الرسمي القديم أيضًا للتوافق مع الروابط الموجودة.
- يرسل الباك كل سطر طلب إلى Paymob كمجموعة واحدة: `amount` هو إجمالي السطر، و`quantity` تساوي 1، والاسم والوصف يوضحان عدد الوحدات الفعلي وسعر الوحدة. هذا يحافظ على تطابق إجمالي البنود ورسوم التوصيل مع إجمالي الطلب، ويزيل الغموض في طريقة احتساب كمية البند لدى المزود.
- يميز الباك رفض الإعداد الصريح بحالات HTTP `400/401/403/404/406` بالكود `payment_setup_rejected`، ويترك الطلب محفوظًا والدفع `pending`. لا توجد إعادة تلقائية للطلب الخارجي؛ أخطاء المفاتيح أو إعدادات التكامل تحتاج مراجعة قبل محاولة المستخدم التالية.
- يظل timeout أو الرد غير المؤكد أو غير القابل للتحقق في `initialization_unknown`. لا يعيد الكود إنشاء جلسة قد تكون موجودة بالفعل، ولا يغيّر حالة الدفع إلى `paid` من المتصفح.
- عند نجاح تجهيز الجلسة، تنتقل الواجهة في نفس التبويب. إذا لم يفتح المتصفح الصفحة تلقائيًا، يظهر رابط مباشر صالح إلى Paymob وزر لعرض حالة الطلب. يمنع الفرونت إعادة إرسال checkout بعد تجهيز الرابط.
- إذا فشل تجهيز الدفع، يظهر السبب الآمن في صفحة الطلب بدل الاعتماد على رسالة مؤقتة فقط. تسجل الخدمة كود الخطأ وHTTP status دون المفاتيح أو نص رد المزود أو بيانات البطاقة.

## التحقق الذي تم

تم تنفيذ تشخيص Sandbox يدوي ببيانات افتراضية، دون إدخال PAN أو CVV أو تنفيذ تحصيل. محاولة بكمية 2 وإجمالي سطر مع إبقاء `quantity=2` رُفضت بحالة HTTP `406`. بعد تجميع السطر باستخدام `quantity=1` وكتابة الكمية الفعلية في الاسم والوصف، أعاد Paymob HTTP `201` وجلسة دفع صالحة. التشخيص استخدم رسوم توصيل صفرية. هذا يثبت أن صيغة الطلب المعدلة فتحت البوابة، لكنه لا يحدد بأثر رجعي سبب فشل الطلبين القديمين.

تم فتح الجلسة الجديدة بمتصفح والتحقق من وجود حقول رقم البطاقة، وتاريخ الانتهاء، ورمز الأمان على نطاق Paymob بحالة HTTP `200`. لم تتم تعبئة الحقول أو الضغط على زر الدفع. استُخدمت جلسة مؤقتة في الذاكرة ولم تُضف طلبات أو بيانات عملاء إلى قاعدة Foodify.

نجح بناء الفرونت وفحص صياغة ملفات Python المعدلة. لم تُنشأ أو تُشغّل unit tests أو integration tests.
