# شرح شغل التيمات — Foodify Sprint 3

الدليل ده يشرح إيه اللي اتعمل في Foodify حتى **Sprint 3** (بوابات العمل المفصولة للأدمن والمدير والمطبخ والمندوب والعميل، الإشعارات الفورية، وإصلاح وصول البريد الإلكتروني)، اتعمل إزاي، استخدمنا إيه، وليه اتقسم بالطريقة دي. شرح Backend بالإنجليزي، وبقية الفصول بالعربي مع المصطلحات التقنية المعتادة.

## ابدأ بالرحلة الكبيرة (من العميل إلى التوصيل)

```text
العميل يفتح Marketplace (/)
  → يقرأ المتاجر والمنتجات من MySQL عبر FastAPI
  → يضيف منتجًا في سلة مستقلة لمتجر، ويؤكد الطلب وعنوان التوصيل (بورسعيد / بورفؤاد)
  → يُنشأ الطلب (pending) + Paymob / InstaPay / Cash
  → إشعار فوري للمدير (/operations أو /manager) والمحضّر (/kitchen)
  → المدير يؤكد الطلب ويعيّن محضّرًا ومندوبًا من القوائم، ويُضيف مطاعم وأصناف منيو
  → المحضّر يستلم إشعار الطلب في (/kitchen) ويحوّله إلى preparing ثم ready_for_pickup
  → المندوب يستلم إشعار الجاهزية في (/delivery) ومعه عنوان العميل الكامل + رقم الهاتف
  → المندوب يؤكد الاستلام (picked_up) ثم التسليم (delivered) → إشعار العميل والمدير
  → الأدمن (/admin) ينشئ حسابات الموظفين المفعّلة فورًا ويدير الأدوار والصلاحيات
```

منظومة الحسابات كانت أساس Sprint 1، والكتالوج والسلال والدفع أساس Sprint 2، وفي **Sprint 3** أضفنا فصل البوابات الخمس حسب الدور (`customer`، `admin`، `operations_manager`، `restaurant_manager`، `order_preparer`، `courier`) مع نظام إشعارات (`12` حدثًا)، وتوجيه الدخول التلقائي `loginDestination(user)`، وإصلاح وصول البريد عبر `HTML Multipart` + `Gmail SMTP / Resend / Brevo`.

## تقسيم الشغل

| التيم | مسؤوليته | بيسلّم إيه؟ |
|---|---|---|
| Frontend | تجربة المستخدم، المكونات، الصفحات، الحالة، وعرض النتائج والأخطاء. | React + TypeScript، صفحات مترابطة وHTTP adapters. |
| Backend | قواعد العمل والهوية والملكية والصلاحيات والمعاملات وحفظ البيانات والدفع الموثوق. | FastAPI endpoints، MySQL schema، services، repositories، migrations. |
| Integration | تطابق الطلبات والاستجابات بين الطرفين ومسار الجلسة والدفع وتوحيد الأخطاء. | DTO mapping، HTTP transport، عقود Postman واختبارات اتصال الوحدات. |
| Deployment | تجهيز البيئات والخدمات والإعدادات وترتيب الإصدار والمراقبة. | Docker للتطوير، Vercel، FastAPI Cloud، Aiven، CI وإعداد callbacks. |

الفصل بين التيمات لا يعني إن كل تيم يعمل نسخة مختلفة من قواعد الحسابات أو السعر. الباك هو مرجع الصلاحيات والأموال وحالة الطلب. الفرونت والـIntegration يرسلان النية ويعرضان النتيجة.

## إيه اللي الدليل ما يعتبرهوش دليلًا عليه؟

وجود كود callback واختبار توقيعه لا يثبت أن حساب Paymob في الإنتاج مفعّل. نجاح اختبارات Google بمحاكاة مزود الخدمة لا يثبت أن redirect URI الموجود في Google Console مطابق. ونجاح SQLite tests لا يثبت سلوك MySQL row locks تحت الضغط.

النتائج الحالية تخص اختبارات محلية معزولة والبناء والتحقق من العقود. فحوص حسابات المزودين والخدمات المنشورة ونشر التغييرات إجراءات مستقلة. شرح كل حد من الحدود دي موجود في فصل [الاختبارات](testing.md) و[Deployment](deployment.md).
