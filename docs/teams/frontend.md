# شرح فريق Frontend — Sprint 2 وSprint 3

الملف ده يشرح الشغل الموجود فعلًا في كود Foodify حتى **Sprint 3**، وإزاي أجزاء الفرونت تفصل بوابات العمل الخمس وتكمّل رحلة المستخدم من مشاهدة المتاجر لحد التوصيل. الشرح عربي مع الاحتفاظ بالمصطلحات التقنية بالإنجليزي عشان الفريق يقدر يناقش الكود ويشرحه. تفاصيل تنفيذ السيرفر موجودة في [شرح Backend](backend.md)، وتفاصيل الاتصال بين الطرفين في [شرح Integration](integration.md).

## 1. الفريق كان مسؤول عن إيه؟

فريق Frontend مسؤول عن الصفحات اللي المستخدم بيتعامل معاها، وإدارة حالتها، والتحقق المبدئي من المدخلات، وعرض البيانات والأخطاء القادمة من API. في Sprint 2 الشغل شمل Marketplace والمتاجر والمنتجات والسلال وCheckout والدفع وسجل الطلبات والتتبع وشاشة إدارة الطلبات. اتعملت كمان إصلاحات في تأكيد البريد وOAuth لأنها جزء لازم لإكمال رحلة الطلب.

مثلًا المستخدم بيضغط «إضافة للسلة»، الفرونت يرسل العملية ويعرض السلة اللي رجعت من السيرفر. حساب السعر النهائي وحماية ملكية السلة وتسجيل الطلب في MySQL مسؤولية الباك. تقسيم المسؤولية ده يمنع إن تغيير مبلغ في DevTools يغيّر السعر الحقيقي للطلب.

| الجزء | مسؤولية الفرونت |
| --- | --- |
| المتاجر والمنتجات | عرض نتيجة API مع البحث والفئات والترتيب والصور. |
| السلة | اختيار الكمية وإرسال الإضافة والتعديل والحذف لمتجر محدد. |
| Checkout | اختيار عنوان ووسيلة دفع وإظهار المبلغ ثم إرسال طلب منضبط. |
| الدفع | طلب رابط البوابة والتحقق من وجهته والانتقال إليه وعرض الحالة. |
| الحساب | تسجيل الدخول والتأكيد وOAuth واستكمال بيانات التوصيل. |
| إدارة الطلبات | عرض الطلبات وإرسال المرحلة التالية للمستخدم المخول. |

## 3. تقسيم الكود ومعنى Clean Architecture هنا

التقسيم الأساسي حسب الـFeature: `auth` للحساب والدخول، و`account` للملف والعناوين، و`marketplace` للمتاجر والسلال والطلبات والدفع. جوه كل Feature فيه طبقات، بدل ملف كبير يحتوي الشاشة والـfetch والتحقق وكل التفاصيل.

```text
front/src/
├── app/                         تهيئة التطبيق والخدمات والـRouter والـProviders
├── features/
│   ├── auth/                    الدخول والتسجيل والبريد وOAuth
│   ├── account/                 بيانات الحساب وعناوين التوصيل
│   └── marketplace/
│       ├── domain/              النماذج والعقود
│       ├── application/         خطوات الاستخدام والتحقق المبدئي
│       ├── infrastructure/      تنفيذ HTTP وDTOs وMappers
│       └── presentation/        الصفحات والمكونات والـHooks والتنسيق
├── infrastructure/http/         الاتصال والأخطاء وإدارة جلسة المتصفح
└── shared/                      عناصر العرض والأخطاء والـHooks المشتركة
```

### Domain: إيه البيانات اللي التطبيق فاهمها؟

`domain/models.ts` يعرف أنواع زي `Merchant` و`Product` و`Cart` و`Order`. فيه كمان Interfaces زي `CatalogRepository` و`CartRepository` و`OrderRepository` و`PaymentRepository`. الـInterface بتحدد العمليات المطلوبة من غير ما تفرض إن مصدر البيانات HTTP أو أي تنفيذ بعينه.

مثلًا `OrderRepository` يعرف عملية `checkout`، لكن ما يعرفش تفاصيل `fetch` أو اسم Header. ده يقلل اعتماد منطق التطبيق على وسيلة الاتصال، ويسمح للاختبار إنه يحقن تنفيذ صغير بدل الاتصال بشبكة حقيقية.

### Application: العملية تمشي إزاي؟

الـUse Case دالة باسم واضح تنفذ هدف واحد. `createUpdateQuantity` يرفض كمية غير صحيحة قبل الاتصال، و`createCheckout` يمرر بيانات الـCheckout المطلوبة، و`createStartPayment` يفحص رابط بوابة الدفع وصلاحيته قبل ما الصفحة تنتقل له.

مصانع الدوال دي تستقبل Repository كاعتماد: `createCheckout(orderRepository)`. اسم الأسلوب `Dependency Injection`؛ الاعتماد بيتبعت للوظيفة بدل ما الوظيفة تنشئ HTTP Client بنفسها. تطبيقه هنا بسيط ومناسب لحجم المشروع.

### Infrastructure: نكلم الباك إزاي؟

`HttpCatalogRepository` و`HttpCartRepository` و`HttpOrderRepository` و`HttpPaymentRepository` تعرف مسارات API والـDTOs. الـDTO هو شكل البيانات على الشبكة؛ مثلًا الباك يستخدم `restaurant_id`، بينما النموذج داخل الواجهة يستخدم `restaurantId`.

الـMapper يحول الشكل القادم من السيرفر إلى شكل مناسب للتطبيق. مثال مهم: `HttpOrderRepository.checkout` يحول `expectedTotal` إلى `expected_total`، ويضيف `Idempotency-Key` عن طريق الـClient. الصفحة مش محتاجة تعرف أسماء الحقول دي.

### Presentation: نعرض ونسمع أفعال المستخدم

الصفحات تجمع Components، وتقرأ الخدمات من `useServices`، وتدير الاختيارات الظاهرة. `CheckoutPage` تعرف العنوان ووسيلة الدفع المختارين، و`CartPanel` يعرض بنود السلة. تفاصيل إرسال HTTP موجودة في Infrastructure، وتفاصيل قواعد الباك تفضل على السيرفر.

تطبيق `Single Responsibility` يظهر في إن `FoodPhoto` مسؤول عن الصورة وبديلها، و`OrderTimeline` عن مراحل الطلب، وRepository عن الاتصال. وجود ملفات منفصلة بيخلي تعديل صورة أو API أقل تأثيرًا على بقية الرحلة.

## 4. إزاي التطبيق بيركب الطبقات مع بعض؟

`front/src/app/services.ts` هو `Composition Root`: ينشئ `BrowserSessionManager` ثم `FetchHttpClient` ثم Repositories، ويوصلها بالـUse Cases. `ServicesProvider` يتيح الناتج لمكونات React. اختيار الـImplementations بيتم في مكان معروف بدل تكراره داخل كل صفحة.

مسار عملية نموذجية:

```text
زر في CheckoutPage
    → createCheckout
    → OrderRepository interface
    → HttpOrderRepository
    → FetchHttpClient
    → FastAPI
    → DTO response
    → Mapper
    → Order model
    → صفحة الطلب
```

## 5. مصدر البيانات: MySQL عبر FastAPI

بيانات المطاعم والحلويات والبقالة والمنتجات والأسعار وروابط الصور تأتي من API، والباك يقرأها من MySQL. الفرونت ما بيتصلش بقاعدة البيانات مباشرة، وما عندوش Username أو Password للداتابيز.

في المشروع ملفات قديمة تحمل أسماء `demo` من مرحلة عرض التصميم، لكن `createAppServices()` يختار تنفيذ API. إعداد التشغيل والبناء يرفض أي `VITE_DATA_SOURCE` غير `api`. تعطل الباك يظهر Error state للمستخدم؛ مش بيستبدل بياناته بقائمة محلية مخفية.

ملف `back/app/ordering/data/demo-catalog.json` تابع للباك كـSeed، يعني إدخال عينة بيانات في قاعدة البيانات. كون المنتجات تجريبية ما يمنعش إنها محفوظة في MySQL وتيجي للفرونت من نفس API الحقيقي. دي نقطة مختلفة عن JavaScript array جوه الواجهة.

الصور المعروضة روابط محفوظة في بيانات المتاجر والمنتجات. `FoodPhoto` يسمح بمضيفي صور معروفين ويستخدم أيقونة بديلة لو الرابط غير صالح أو التحميل فشل. `MerchantLogo` يسمح بمسارات صور محلية محددة أو المضيفين المعتمدين. الصورة البديلة لا تغير اسم المنتج أو سعره أو بياناته.

## 6. صفحات Marketplace والبحث

`MarketplacePage` تعرض المتاجر، وفوقها الفئات وأقسام المطاعم والحلويات والبقالة والمفضلة والتوصيل المجاني. البحث والترتيب والفلاتر تتحول إلى Query Parameters يرسلها `HttpCatalogRepository` للباك.

الفلاتر الموجودة تشمل نوع المتجر، والفئة، والنص، والأعلى تقييمًا، والأسرع، ورسوم التوصيل، والتوصيل المجاني، وحد أقصى لوقت التوصيل. الاختيار يتحفظ في عنوان الصفحة عن طريق `useSearchParams` عشان الرجوع والتنقل يحافظوا على سياق المستخدم.

قسم العروض الحالي يعرض التوصيل المجاني حسب البيانات الفعلية. ما بيخترعش سعرًا قديمًا أو نسبة خصم مش راجعة من الباك. المفضلة مرتبطة بالحساب، وفتحها من غير جلسة يوضح إن المستخدم يحتاج تسجيل الدخول.

`MerchantPage` تحمل بيانات المتجر وقائمة المنتجات، وتعرض `ProductCard` لكل منتج و`CartPanel` لسلة المتجر. القائمة تدعم قراءة صفحات API المتتابعة عشان المنتجات ما تختفيش عند تجاوز حجم صفحة واحدة.

## 8. السلال المستقلة: متجر واحد لكل طلب

المستخدم يقدر يضيف منتجات من متجر أ، وبعدها يفتح متجر ب ويضيف منه. التطبيق يحتفظ بسلة لكل متجر، ويعرضهم في `CartsPage`. الـCheckout يتحدد بـ`restaurantId` ويعمل طلبًا واحدًا خاصًا بسلة المتجر المختار.

كل عمليات `add` و`quantity` و`remove` و`clear` بتتلقى هوية المتجر. عند رجوع نتيجة تعديل، `MarketplaceProvider` يستبدل سلة المتجر ده فقط داخل الحالة؛ السلال الأخرى تفضل موجودة. إفراغ سلة له تأكيد مرتبط بالسلة المعروضة.

حالة السلال والمفضلة مرتبطة بهوية الحساب. عند الخروج أو تبديل المستخدم، النتائج المتأخرة من Requests الحساب القديم ما ينفعش تظهر للحساب الجديد. الـProvider يقارن الجلسة الحالية قبل نشر أي استجابة.

لو قراءة السلال بدأت، وبعدها اكتمل تعديل كمية، الرد القديم للقراءة ممكن يكون أقدم من التعديل. اتضافت Revisions وRead counters تمنع إن الرد القديم يستبدل النتيجة الجديدة. أثناء تعديل السلة فيه منع لتعديل متداخل، وتبديلات المفضلة تتنفذ في Queue عشان نتيجة الضغطات تفضل بالترتيب.

الأسعار تتنقل في النماذج كسلاسل عشرية مثل `179.50`. العرض بالجنيه المصري يستخدم `Intl.NumberFormat`؛ أرقام الواجهة ليست اعتماد السيرفر لحساب المستحق.

## 9. Checkout ومنع الطلبات المكررة

`CheckoutPage` تحمل السلة والمتجر والعناوين ووسائل الدفع بالتوازي باستخدام `Promise.all`. بعدها المستخدم يراجع عنوانه وبنود الطلب ورسوم التوصيل والإجمالي ويختار وسيلة متاحة.

قبل إرسال الطلب، الفرونت يبعت `restaurantId` و`addressId` و`method` و`expectedTotal` و`cartRevision`. المبلغ المتوقع هو اللي المستخدم شافه، ونسخة السلة هي النسخة اللي راجعها. السيرفر يقارنهم بالوضع الحالي ويرفض الطلب لو الأسعار أو السلة اتغيرت.

`Idempotency-Key` هو مفتاح للمحاولة يمنع تكرار إنشاء نفس الطلب عند إعادة الإرسال. الفرونت يولد `crypto.randomUUID()`، ويربطه بـFingerprint لبيانات المحاولة، ويحفظه في الذاكرة و`sessionStorage` بنطاق الحساب والمتجر.

لو حصل Timeout، ممكن السيرفر يكون حفظ الطلب فعلًا رغم إن الرد ما وصلش. إعادة نفس المحاولة تستخدم نفس المفتاح؛ الباك يقرر إنها إعادة لنفس العملية. تغيير العنوان أو السلة أو وسيلة الدفع يغير الـFingerprint ويعمل محاولة مختلفة. الـHeader وحده لا يكفي؛ تطبيقه الحقيقي موجود في الباك.

فيه `inFlight` guard يمنع ضغطتين متتاليتين قبل تحديث React للزر، وحالة `busy` توقف الاختيارات أثناء الإرسال. الـGuard يحسن التفاعل، وIdempotency على السيرفر يحمي تكرار HTTP حتى لو المستخدم تجاوز الواجهة.

## 10. الدفع: إيه اللي الفرونت بيعمله بالضبط؟

وسائل الدفع تقرأ من `/payments/methods`. وجود تصميم لوسيلة مش معناه إنها مفعلة؛ قيمة `enabled` القادمة من الباك هي اللي تحدد اختيارها.

| الوسيلة | الرحلة |
| --- | --- |
| Card | حفظ الطلب، ثم طلب Hosted Checkout من Paymob والانتقال إليه. |
| Vodafone Cash وOrange Cash | نفس فكرة Hosted Checkout مع إعداد Wallet على الباك. |
| InstaPay | عرض بيانات المستلم المخزنة مع الطلب، ثم إرسال Reference للمراجعة. |
| Cash | حفظ الطلب وعرض إن المبلغ مستحق عند الاستلام. |
| Simulated | يظهر فقط لو الباك فعله ويبين إنه تجربة بدون تحصيل. |

`createStartPayment` يسمح فقط بوجهات Paymob المعتمدة: `https://eg.checkout.paymob.com/`، والمسار القديم المتوافق `https://accept.paymob.com/unifiedcheckout/`. بيفحص HTTPS والمضيف والمسار وعدم وجود Username أو Password أو Fragment، وإن `publicKey` و`clientSecret` موجودين مرة واحدة وغير فاضيين، وصلاحية الرابط لم تنتهِ.

بعد التحقق، الصفحة تستخدم `window.location.assign`. لو الانتقال ما اكتملش يظهر رابط واضح لبوابة نفس الطلب. لو تجهيز الدفع فشل، المستخدم ينتقل لصفحة الطلب برسالة مناسبة؛ الطلب المحفوظ ما يضيعش وسط رسالة عامة.

Foodify ما فيهش حقول لتجميع PAN أو CVV أو OTP؛ إدخالها يحصل على بوابة الدفع. مفاتيح Paymob السرية موجودة على الباك. رابط Checkout المؤقت يُستخدم لإكمال الجلسة ولا يتحفظ كتخزين دائم.

العودة من Paymob ببارامتر مثل `success=true` مش دليل تحصيل. صفحة الطلب تقرأ الحالة من API، والباك يتحقق من Callback وتوقيعه. في `initialization_unknown` ما بنبدأش عملية جديدة تلقائيًا لأن نتيجة الاتصال بالمزود غير معروفة وقد يؤدي التكرار إلى أكثر من عملية.

محليًا الوصول إلى صفحة البطاقة ممكن، لكن استقبال Callback من Paymob يحتاج HTTPS متاحًا من الإنترنت. الاختبارات بالـMocks تثبت سلوك كود الواجهة؛ لا تثبت خصم أموال أو إعداد حساب Paymob الحقيقي.

## 11. سجل الطلبات والتتبع

`OrdersPage` تعرض سجل طلبات الحساب مع Pagination، و`OrderPage` تعرض البنود والعنوان وحالة الدفع ومراحل التنفيذ وإمكانية الطباعة. البيانات المعروضة Snapshot للطلب كما يرجعها الباك، مش إعادة تجميع لسلة المستخدم الحالية.

`useOrder` تعمل Polling كل خمس ثوانٍ إذا التبويب ظاهر، وتتوقف بعد `delivered` أو `refunded`. عند ترك الصفحة يتلغى الـRequest بالمـ`AbortController` ويتلغى المؤقت. حالة الطلب مرتبطة بالحساب ورقم الطلب عشان النتيجة القديمة ما تظهرش في صفحة مختلفة.

التتبع هنا Timeline للحالات المحفوظة: `placed → preparing → ready → out_for_delivery → delivered`. مش تتبع GPS حي، ومافيش حركة مندوب مصطنعة. فصل حالة الدفع عن حالة تجهيز الطلب بيوضح فرق «بانتظار الدفع» و«بيتحضر».

## 12. شاشة Operations وإصلاح الانتقالات

`OperationsPage` تتيح اختيار متجر وعرض طلباته وتحديث القائمة والانتقال بين صفحات النتائج. `OperationalOrder` تعرض معلومات الطلب والإجراء المناسب للمرحلة، ومراجعة Reference التحويل عند الحاجة.

الواجهة تعرضها لأدوار `admin` و`operations_manager`، لكن ده مش بديل عن Authorization في API. كل تغيير مرحلة أو مراجعة تحويل لازم يمر على تحقق الباك من الدور والصلاحية والانتقال.

اتصلحت `nextOrderStage`: الحالة لازم تكون فعلًا داخل تسلسل التنفيذ عشان يطلع لها Next stage. قبل التصحيح، التعامل مع فهرس غير موجود كان ممكن يعرض أول مرحلة لحالة زي `cancelled` أو `awaiting_payment`. حاليًا الحالات دي والحالة النهائية أو المجهولة ما بيطلعش لها زر تقدم غير مناسب.

## 13. تأكيد البريد وOAuth واستكمال البيانات

الروابط الخارجية من البريد تكون مثل `/verify-email#token=...` أو `/reset-password#token=...`. قبل بدء React، `normalizeExternalLinks` يحولها للمسار الصحيح داخل `HashRouter`. `useSensitiveSearchParam` يحتفظ بالقيمة المطلوبة للصفحة ويزيلها من عنوان التنقل بدل استمرار عرضها فيه.

صفحة التأكيد لا تستهلك Token بمجرد فتح الرابط؛ المستخدم يضغط «تأكيد البريد ومتابعة بياناتي». `HttpAuthRepository.confirmEmail` يطلب `/auth/browser/verify-email`، ويقبل جلسة المتصفح الجديدة، و`ConfirmEmailPage` تحدث `SessionProvider` وتختار وجهة الحساب.

`accountDestination` يوجه المستخدم الذي ينقصه الهاتف إلى `/onboarding/profile`، وبعد حفظ الاسم والهاتف ينتقل لإضافة العنوان. لو الهاتف موجود والعنوان الافتراضي ناقص يفتح `/onboarding/address`، ولو البيانات مكتملة يفتح الحساب. المستخدم الجديد ما يرجعش لإدخال Email وPassword بعد نجاح التأكيد.

بدء Google أو Facebook يمر على الباك. `BrowserOAuthFlow` ينشئ قيمة عشوائية `binding verifier`، ويرسل Challenge مشتق منها، ويحفظ الـVerifier مؤقتًا في `sessionStorage` للتبويب. عند الرجوع يستبدل Ticket مع الـVerifier على `/auth/browser/oauth/complete`، ثم يقبل الجلسة ويمسح القيم المؤقتة.

وجهة Authorization القادمة من الباك يتم فحصها قبل الانتقال لمضيف Google أو Facebook والمسار المتوقع، لمنع توجيه المستخدم إلى عنوان مشابه ضار. الـVerifier ده ربط لتبادل تذكرة التطبيق بالتبويب الأصلي؛ تفاصيل تبادل OAuth مع المزود على الباك.

اتصلحت مشكلة اختلاف `localhost` و`127.0.0.1`: الاتنين لهم `sessionStorage` منفصل رغم إنهم على نفس الجهاز. التشغيل المحلي على منفذ `5173` يوحد الوجهة إلى `127.0.0.1` قبل إنشاء الـVerifier ويحافظ على المسار والـQuery والـFragment. التحويل محدد للتطوير، ولا يغير دومين Production.

## 14. الجلسة وRace Conditions

`BrowserSessionManager` يحتفظ بـAccess Token في الذاكرة. Refresh Token في `HttpOnly Cookie` يرسلها المتصفح مع `credentials: include`؛ JavaScript ما بيقرأهاش. التطبيق ما بيحطش Access أو Refresh Token في `localStorage`.

`FetchHttpClient` يضيف Bearer عند الطلب المحمي، و`Accept` و`X-Foodify-Client`. لو Access Token انتهى وظهر `401` يحاول استرجاع الجلسة ثم يعيد الطلب مرة بالجلسة الصحيحة. لو الحساب تغير أثناء الطلب، ما يعيدش عملية الحساب أ باسم الحساب ب.

لما أكتر من Request يحتاج Refresh في نفس اللحظة، مدير الجلسة يستخدم Promise واحدة بدل تدوير Cookie كذا مرة. كمان فيه Revision يمنع Refresh قديم يفشل بـ`401` من محو Login جديد، أو رد قديم ناجح من إعادة جلسة بعد Logout.

`SessionProvider` ما يبدأش استعادة Cookie قديمة عند تحميل صفحة تأكيد البريد أو تبادل OAuth؛ الصفحات دي بتنشئ جلسة جديدة في نفس الوقت. منع التعارض ده يعالج سيناريو نجاح الدخول ثم الرجوع لشاشة Login بسبب رد Refresh متأخر.

## 15. UX وAccessibility والأداء

التصميم عربي بـ`lang="ar"` و`dir="rtl"`، وألوان متناسقة وأزرار مشتركة. أسماء الإجراءات توضح النتيجة: «أكّد الطلب» للكاش، و«كمّل للدفع الآمن» للبوابة، و«احفظ الطلب واعرض بيانات التحويل» لـInstaPay.

حالات Loading وError وEmpty واضحة، وفيها إعادة محاولة وقت الحاجة. النماذج لها Labels، ومجموعات الاختيار تستخدم `fieldset` و`legend`، ورسائل الخطأ `role="alert"`، وحالات المعلومات `role="status"`. الأيقونات الزخرفية `aria-hidden` حتى لا تكرر نصًا مسموعًا بلا فائدة.

`RouteEffects` تغير عنوان الصفحة وتعيد التركيز لعنوان المحتوى بعد التنقل. الصور لها Lazy Loading، وصور المنتجات الزخرفية لا تكرر اسم المنتج لقارئ الشاشة. بعض الصفحات الأثقل مثل Checkout والطلبات وOperations تتحمل بـ`React.lazy` و`Suspense` بدل إضافتها كلها إلى البداية.

`useResource` يلغي Requests عند تغيير الصفحة، ويتأكد إن الاستجابة تخص عملية التحميل الحالية. التحميل المتوازي يقلل الانتظار لما البيانات مستقلة. ده تحسين أداء عملي؛ الملف ما بيدعيش قياسات Lighthouse أو تدقيق Accessibility آلي لم يتم تنفيذه.

`vite.config.ts` يضيف Production CSP يحدد مصادر Scripts وStyles وFonts والصور والاتصال. `assetsInlineLimit: 0` يخلي ملفات الخطوط تتخدم من نفس الأصل، بما يتوافق مع `font-src 'self'`. حماية المتصفح مكملة لتحقق الباك وليست بديلًا عنه.

## 16. رحلة كاملة نقدر نشرحها للدكتور

1. عميل يسجل أو يكمل Google. `auth` تنشئ جلسة، و`accountDestination` تحدد البيانات الناقصة.
2. يضيف الاسم والهاتف والعنوان في `account`. القيم تتبعت لـAPI وتتحدث بيانات الحساب.
3. يفتح Marketplace. `HttpCatalogRepository` يقرأ المتاجر والفئات من الباك، وتعرضهم Components.
4. يضيف منتجًا من متجر أ ومنتجًا من متجر ب. `MarketplaceProvider` يحتفظ بنتائج السلتين منفصلتين.
5. يفتح Checkout لمتجر أ، ويختار عنوانًا وCard. الصفحة ترسل نسخة السلة والإجمالي ومفتاح المحاولة.
6. الباك يتحقق ويحفظ الطلب. الفرونت يستقبل `Order` عن طريق Mapper، ثم يطلب بدء الدفع للطلب ده.
7. `createStartPayment` يفحص رابط Paymob، وينتقل المتصفح لبوابة الدفع. بيانات البطاقة لا تدخل Foodify.
8. بعد العودة، `OrderPage` تقرأ حالة الباك وتعرضها. الموظف المخول يحدث مرحلة التنفيذ من Operations.
9. العميل يشوف تطور الـTimeline، وسلة متجر ب تفضل موجودة لطلب مستقل لاحقًا.

دي رحلة مشتركة: الفرونت ينظم التفاعل والعرض، Integration يطابق العقود والأخطاء، الباك يتحقق ويحفظ، وDeployment يوفر الإعدادات والعناوين والخدمات.

## 17. اختبارات الفرونت: إيه اللي بتثبته؟

اختبارات الفرونت في ملفين: `front/tests/frontend-regressions.test.mjs` يحتوي 48 حالة Regression، و`front/tests/frontend-integration.test.mjs` يحتوي 6 حالات Integration بين Modules الفرونت. الاثنين يستخدموا `node:test` وAssertions، ويشغلوا Vite بـ`middlewareMode` لتحميل Modules TypeScript باستخدام `ssrLoadModule` ونفس Alias `@` الموجود في التطبيق. مش محتاج تشغيل Vite كصفحة متصفح فعلية عشان يختبر الدوال.

اختبارات الـUse Cases تحقن Repositories بسيطة في الذاكرة. اختبارات HTTP تستبدل `globalThis.fetch` بردود محددة، واختبارات الروابط تستخدم بدائل صغيرة لـ`window` و`document` و`sessionStorage`. بعد كل Test يرجع الـGlobals لحالتها لتقليل تأثير اختبار على غيره.

| المجموعة | مثال على اللي بتتحقق منه |
| --- | --- |
| Paymob destination | قبول الروابط المعتمدة ورفض HTTP والمضيف المشابه والمعاملات المكررة والرابط المنتهي. |
| نتيجة دفع غير معروفة | تمرير الخطأ بدون بدء محاولة ثانية تلقائية. |
| External links | توجيه رابط التأكيد وReset Password وOAuth إلى الصفحة الصحيحة. |
| Origin المحلي | توحيد المضيف مع الحفاظ على مسار الرابط، وترك المواقع الأخرى كما هي. |
| Session concurrency | Refresh واحد متزامن ومنع رد قديم من محو Login جديد أو إعادة جلسة بعد Logout. |
| HTTP identity | منع إعادة Request لحساب قديم بتوكن حساب جديد. |
| Email confirmation | استخدام Browser endpoint وقبول الجلسة والتوجيه لاستكمال الهاتف والعنوان. |
| OAuth | رفض التبادل بدون Verifier، وقبول الجلسة ومسح القيمة المؤقتة، ورفض وجهات Authorization الضارة. |
| Cart وCheckout | رفض كمية غير صالحة، والحفاظ على هوية المتجر وRevision وIdempotency-Key. |
| Operations | التقدم داخل الحالات الصحيحة وعدم إعادة فتح طلب ملغي أو غير مدفوع. |

ملف Integration الإضافي يوصل `FetchHttpClient` الحقيقي و`BrowserSessionManager` الحقيقي مع HTTP Repositories وMappers وUse Cases من كود التطبيق. الحد المستبدل هنا هو استجابة HTTP بدل السيرفر الخارجي. ده يقيس اتفاق أجزاء الواجهة مع بعض بدل استبدال كل جزء منفصلًا.

| Integration case | تسلسل الأجزاء الذي يختبره |
| --- | --- |
| Email confirmation | HTTP request ثم DTO mapping ثم قبول الجلسة ثم اختيار Onboarding، ثم استخدام Bearer في طلب تالٍ. |
| Session refresh | رد `401` ثم تدوير الجلسة بالمدير الحقيقي ثم إعادة الطلب مرة بالتوكن الجديد. |
| Merchant carts | طلب سلتين لمتجرين مختلفين ثم Mapping يحافظ على هوياتهم والقيم المالية النصية. |
| Checkout contract | Use Case ثم تحويل DTO وإرسال Header منع التكرار ثم تحويل استجابة الطلب. |
| Hosted payment | طلب رابط الدفع عبر Repository ثم فحص Paymob URL والصلاحية بالـUse Case الحقيقي. |
| API errors | خطأ `409` يصل بكود معروف و`request_id`، مع عرض رسالة آمنة بدل تفاصيل تشخيص داخلية. |

جزء من الاختبارات Unit لدالة معزولة، وجزء اختبار تعاون Modules. سكربت `test:unit` يشغل مجموعة Regression التي تضم أيضًا اختبارات Classes ببدائل لاعتماداتها، و`test:integration` يشغل تركيب Modules الحقيقي الموضح. دول اختبارات منطق الفرونت؛ مش `ReactDOM` rendering tests، ومش Browser E2E، ومش اتصال حقيقي بـMySQL أو Paymob أو حساب Google. Integration Tests الخاصة بالباك تشغل FastAPI مع قاعدة SQLite معزولة، ولها إعداد وشرح مستقل في [شرح Testing](testing.md).

التشغيل من `front/`: `npm ci` لتثبيت نفس Lockfile، و`npm run test:unit` لمجموعة Regression (**49** حالة)، و`npm run test:integration` لمجموعة تركيب Modules (**10** حالات)، أو `npm test` لتشغيل **78** حالة JS معًا (بإضافة اختبارات Proxy وPostman).

## 18. إعدادات التشغيل وحدود مسؤولية الفريق

`VITE_API_BASE_URL` عنوان API العام للواجهة، و`VITE_DATA_SOURCE=api` يثبت مصدر البيانات. قيم `VITE_` تدخل في JavaScript اللي يقدر الزائر يقرأه، لذلك مفاتيح Google/Facebook وPaymob وباسورد MySQL لا توضع فيها. إعداد العناوين وProxy وCORS وHTTPS مشروح في [شرح Deployment](deployment.md).

المفاتيح الصحيحة وRedirect URIs وحسابات المزودين لازمة لتشغيل OAuth الحقيقي، وCallbacks متاحة من الإنترنت لازمة لتأكيد الدفع. الاختبار المحلي المعزول لا يستبدل التحقق من إعداد مزود الخدمة، ولا نعتبر كتابة InstaPay Reference تأكيدًا للتحويل.

التوثيق ده محتوى مرتبط بالكود، وأداة بناء التوثيق تحول Markdown إلى صفحات منظمة. شرح طريقة توليده بـMkDocs وفرقها عن FastAPI OpenAPI موجود في [شرح Documentation](documentation.md). التفسير الصحيح للفريق: الأداة بنت ونظمت صفحات الشرح، وFastAPI ولّد عقود API؛ شرح قرارات الكود نفسه تم إعداده ومراجعته من التنفيذ.
