# Sprint 1: فهم الاختبارات والتوثيق في أساس الحسابات

الفصل ده يشرح إيه اللي لازم يتراجع في أساس الحسابات والعناوين وليه، ثم الفصل التالي يعرض الاختبارات الحالية التي شُغّلت فعلًا على المشروع، بما فيها حسابات Sprint 1 وطلبات ودفع Sprint 2. فصل النطاقين لا يعني أن نتائج الاختبارات كانت موجودة تاريخيًا وقت بداية Sprint 1.

## 1. بنختبر إيه في نظام الحسابات؟

التسجيل مش مجرد إن request ترجع200. المستخدم لا يجب أن يختار دور admin من body التسجيل، ولا لازم نكشف له هل بريد شخص آخر مسجل. كلمة المرور يجب أن تُحفظ hash، ورابط التأكيد له مدة واستخدام واحد، والعنوان يجب أن يظل مملوكًا لصاحب الجلسة.

لذلك نراجع النتيجة من ثلاث زوايا: response صحيحة للمستخدم، حالة قاعدة البيانات بعد العملية، وسلوك الفشل الذي يحافظ على الأمان والبيانات. اختبار النجاح فقط لا يغطي انتهاء token أو محاولة استخدام عنوان مستخدم آخر.

## 2. Unit Test يعني إيه؟

هو اختبار لوحدة صغيرة مع استبدال الاعتماديات التي لا تخص هدف الاختبار. إذا اختبرنا parser لتوكن أو validator لرقم هاتف، لا نحتاج تشغيل MySQL. وإذا اختبرنا تصرف service عند فشل إصدار الجلسة، نستخدم session issuer بديلًا ونراقب commit وrollback بدل الوصول لخدمة حقيقية.

مثال: خدمة تأكيد البريد تستهلك الرمز ثم تطلب إصدار جلسة. نُجبر session issuer البديل على الفشل؛ النتيجة المطلوبة أن يحصل rollback وألا يحدث commit. كده نثبت قرار الخدمة نفسها من غير الاعتماد على شبكة أو مستخدم حقيقي.

## 3. Integration Test يعني إيه؟

هو اختبار أجزاء فعلية متصلة. في مشروعنا نرسل request إلى FastAPI TestClient. تدخل على router وPydantic DTO، ثم service وrepository فعلية ثم SQLite داخل الذاكرة. نقرأ الاستجابة ونتحقق من التغيير المحفوظ.

مثلًا نستدعي register، ونفحص وجود user بدور customer، وأن password_hash ليست كلمة المرور، وأن action token مخزنة كبصمة، وأن outbox فيها مهمة رسالة. بعدها نستهلك token ونجرب الدخول، بدل اختبار كل مرحلة بوظيفة بديلة منفصلة.

قاعدة الاختبار هنا SQLite لتكون معزولة وسريعة. هي لا تثبت أقفال MySQL أو DDL migrations أو تحمل طلبات متزامنة؛ هذه فحوص مختلفة.

## 4. سيناريوهات التسجيل والدخول

| السيناريو | المطلوب التحقق منه |
|---|---|
| تسجيل جديد | user واحدة، customer role، hash سليم، ورسالة عامة دون access token. |
| بريد مسجل سابقًا | لا حساب مكرر ولا رسالة تكشف وجود الحساب. |
| body فيها role أو حقول زائدة | الرفض بدل قبول ترقية صلاحيات من العميل. |
| دخول بكلمة مرور خطأ | رفض عام لا يكشف تفاصيل عن الحساب. |
| بريد غير مؤكد | لا دخول password إلى الحساب قبل إثبات البريد. |
| JWT مزور أو منتهي | رفض الطلب المحمي حتى لو العرض يخفي صفحة الحساب. |

## 5. روابط البريد وكلمة المرور

نراجع انتهاء الرابط، غرضه الصحيح، استخدامه مرة واحدة، ومنع استعمال password-reset token كتأكيد بريد أو العكس. إعادة إرسال التأكيد تجعل الروابط القديمة غير صالحة بحسب قواعد الخدمة.

بعد reset ناجح يجب تغيير hash وإلغاء الجلسات القديمة. لو البريد غير موجود، يظل الرد عامًا حتى لا يتحول endpoint إلى أداة تعداد حسابات. كلمة المرور نفسها لا تظهر في logs أو response.

## 6. الجلسة والـcookies

الـaccess token قصير العمر ويظل في ذاكرة الواجهة. refresh token في HttpOnly cookie لمسارات browser، وخادم الباك يحتفظ بسجلات تسمح بالتدوير والإلغاء. نختبر refresh مرة واحدة، replay لرمز قديم، logout، ومحاولة جلسة لحساب تم تعطيله.

في الفرونت نُبطئ response الاستعادة عمدًا ثم نصدر جلسة جديدة. response القديمة لا يجب أن تمسح الجديدة. ونختبر أن logout ينتظر تدويرًا جاريًا قبل طلب حذف الكوكي. هذه سيناريوهات timing وليست مجرد فحص اسم endpoint.

## 7. العناوين وملكية البيانات

المستخدمA لا يقرأ أو يعدل عنوانB حتى لو عرف ID. أول عنوان يصبح افتراضيًا، وتغيير الافتراضي لا يترك عنوانين افتراضيين في نفس الوقت من منظور الخدمة. حذف عنوان يستلزم تحديث الملف والعناوين في الواجهة حتى لا تظل defaultAddressId قديمة.

اختبار إضافة عنوان لا يكتفي بـ201؛ يراجع phone وتفاصيل المستلم والحقول الاختيارية والمالك. واختبار التعديل يراجع أن PUT يرسل النموذج الكامل المقبول، دون user_id أو created_at من العميل.

## 8. OAuth

الاختبار المعزول يستخدم مزودًا بديلًا يعيد identity معلومة. نراجع state وticket أحادية الاستخدام وbinding verifier الصحيح، ومنع التبادل من تبويب آخر، وعدم ربط بريد حساب password قائم تلقائيًا.

ده يثبت قواعد تطبيقنا، لكنه لا يثبت إعداد Google Console أو Meta Dashboard أو أن المزود سيقبل redirect URI في بيئة بعينها. اختبار المزود الحي يحتاج إعداد حسابه ورحلة متصفح منفصلة.

## 9. أدوات التوثيق في هذا الأساس

FastAPI يستخرج OpenAPI من routes وDTOs. Swagger UI يعرض العقود ويساعد على تجربة endpoint عند تفعيل docs. هذه أداة توثيق API، وليست شرحًا آليًا لكل قرار معماري.

Markdown يحتوي الشرح الذي نراجعه من المصدر، وMkDocs ينظمه ويبنيه كموقع دليل. Postman collections تحتوي طلبات يدوية جاهزة؛ وجودها لا يعني وجود assertions آلية. وتقارير JUnit تسجل حالات الاختبار المنفذة وتسمح بتوليد فهرس نتائج فعلي.

## 10. ما الذي انتقل إلى Sprint 2؟

نفس SessionProvider وHTTP client ودفتر العناوين والأدوار والصلاحيات يُستخدم في Checkout. لذلك اختبارات الحسابات ظلت جزءًا من مجموعة المراجعة الحالية، بجانب الكتالوج والسلة والدفع. تصحيح تأكيد البريد ليبدأ جلسة مباشرة وإصلاح سباقات refresh وOAuth من إصلاحات الربط اللاحقة، ولا ننسبها إلى نتيجة تاريخية لم تُختبر وقت بداية Sprint 1.
