# Sprint 1: تيم Frontend

## 1. الهدف من السبرينت وحدوده

الهدف في Sprint 1 كان تجهيز رحلة حساب العميل في Foodify: المستخدم يعمل حساب، يؤكد البريد، يدخل لحسابه، يسترجع كلمة المرور عند نسيانها، ويكمل رقم الموبايل وعنوان التوصيل. الصفحات دي هي الأساس اللي رحلة الطلب والدفع في Sprint 2 بتعتمد عليه.

تيم Frontend مسؤول عن الواجهة اللي المستخدم بيشوفها وبيتعامل معاها: ترتيب الشاشات، النماذج، الأزرار، الرسائل، التنقل، وحالة الحساب المعروضة. حفظ المستخدم وكلمة المرور والعناوين والتحقق النهائي من الصلاحيات مسؤولية الباك إند، والفرونت يتعامل مع ده من خلال عقود واضحة.

الفصل ده يشرح نطاق حساب العميل في Sprint 1 باستخدام أسماء الملفات والدوال الموجودة حاليًا. بعض إصلاحات الجلسة وتأكيد البريد تمت في مراجعات لاحقة؛ هنوضحها باعتبارها تحسينات لاحقة للنطاق نفسه، من غير ما ننسب كل إصلاح لتاريخ التنفيذ الأول.

## 2. التقنيات المستخدمة وكل واحدة عملت إيه

`React 19` استخدمناه لبناء الواجهة من مكونات صغيرة. كل مكون بياخد بيانات وإعدادات عبر `props`، ويرجع الشكل المطلوب عرضه. `useState` يحتفظ بقيم الحقول، و`useEffect` يدير الآثار الجانبية، و`Context` يوزع خدمات التطبيق وحالة الجلسة.

`TypeScript 5.9` أضاف أنواعًا للعقود والمدخلات والنتائج. مثلًا `UserProfile` يحدد شكل الحساب، و`AddressInput` يحدد بيانات العنوان المطلوب حفظه. إعداد `strict` يساعد على اكتشاف استخدام قيمة ناقصة أو نوع غير مناسب قبل تشغيل الموقع.

`Vite 8` مسؤول عن تشغيل سيرفر التطوير وتحديث المكونات أثناء التعديل باستخدام HMR، وبعد الانتهاء بيبني ملفات المتصفح داخل `front/dist`. هو أداة تشغيل وبناء للفرونت؛ مش هو سيرفر الـAPI ومش مسؤول عن قاعدة البيانات.

`React Router 7` مسؤول عن التنقل بين الصفحات وحماية بعض المسارات. المشروع يستخدم `HashRouter`، لذلك مسار مثل `/#/login` يتفسر داخل React. الجزء اللي بعد `#` لا يتحول إلى طلب صفحة مستقلة من سيرفر الاستضافة.

استخدمنا `Lucide React` للأيقونات، و`IBM Plex Sans Arabic` للخط العربي، وCSS لتنسيق الألوان والمسافات والتخطيطات وحالات التركيز. الخط مستورد من حزمة محلية في المشروع عشان ما يعتمدش على تحميله من خدمة خطوط خارجية أثناء فتح الصفحة.

الاتصال بالشبكة يتم بـ`Fetch API` داخل طبقة infrastructure. لا يوجد Redux أو Axios أو مكتبة نماذج خارجية ضمن التنفيذ الحالي؛ الحالة البسيطة موزعة بين React state وContext، وده مناسب لحجم الحساب والعمليات الموجودة.

## 3. شكل الواجهة وتجربة الاستخدام

التصميم عربي باتجاه `RTL`، بلون أحمر للإجراء الأساسي، وخلفيات بيضاء ونصوص داكنة. الهدف إن المستخدم يعرف يعمل إيه في كل شاشة من العنوان والزر الرئيسي، من غير ازدحام خيارات أو تفاصيل تقنية تخص المطورين.

تقسيم الشاشة والتنسيق المشترك موجودان في `front/src/app/layouts/account-layout.tsx` و`brand-panel.tsx`. صفحة الدخول وصفحة إنشاء الحساب تستخدمان نفس اللغة البصرية، بينما محتوى النموذج والعنوان يتغير حسب المهمة.

الأزرار والحقول مش معمولة من الصفر في كل صفحة. `Button` و`Field` و`PasswordField` و`PageHeading` و`FormError` موجودة في `front/src/shared/ui`. ده يحافظ على تناسق المقاسات، النصوص، رسائل الخطأ، وحالة الانتظار.

الموبايل له تخطيط مناسب للمساحة المتاحة. الحقول اللي تحتاج قراءة من اليسار لليمين، مثل البريد ورقم الموبايل، لها `dir="ltr"` حتى لو الصفحة كلها عربية. ده يقلل لخبطة قراءة الأرقام والرموز.

## 4. تقسيم المشروع حسب الوظيفة

بدل تجميع حساب العميل كله في ملف واحد، التنفيذ مقسوم إلى feature اسمها `auth` للمصادقة، وfeature اسمها `account` للملف الشخصي والعناوين. كل واحدة بداخلها domain وapplication وinfrastructure وpresentation.

| المكان | المسؤولية | مثال |
| --- | --- | --- |
| `features/auth` | التسجيل والدخول والبريد وOAuth | `sign-in/use-case.ts` |
| `features/account` | الملف الشخصي والعناوين | `save-address/use-case.ts` |
| `shared` | عناصر قابلة لإعادة الاستخدام | `ui/field.tsx` |
| `app` | تركيب التطبيق والخدمات والمسارات | `services.ts` |

داخل `front/src/features/auth/application/sign-in` يوجد `dto.ts` و`use-case.ts`. كده عملية تسجيل الدخول لها مدخلاتها وتنفيذها الواضح، بدل ما تكون مجرد جزء ضخم وسط ملف المستخدم. نفس التنظيم موجود لإنشاء الحساب، تأكيد البريد، إعادة ضبط كلمة المرور، والخروج.

## 5. تطبيق Clean Architecture بصورة مبسطة

`domain` يحتوي النماذج والواجهات والتحقق العام، من غير اعتماد على React أو DOM. مثلًا `AuthRepository` يحدد العمليات المطلوبة، لكنه ما يعرفش الـURL ولا طريقة عرض النموذج ولا إزاي المتصفح يبعث الطلب.

`application` يحتوي use case لكل عملية. الـuse case يستقبل DTO، ينظف المدخلات ويتحقق منها ثم ينادي repository interface. مثال `createSignIn` ينتج دالة الدخول التي تستخدم `normalizeEmail` و`validatePassword` قبل تفويض التنفيذ.

`infrastructure` تنفذ العقود عمليًا. `HttpAuthRepository` يحول المدخلات إلى جسم HTTP، ينادي endpoint، ويحول الرد إلى نموذج حساب. `presentation` تعرض النموذج وتتعامل مع النجاح والخطأ والتنقل.

مسار تسجيل الدخول مثلًا هو: `LoginPage → services.auth.signIn → use case → AuthRepository → HttpAuthRepository → FetchHttpClient → API`. الرد يرجع في الاتجاه العكسي حتى يصل إلى React في صورة `UserProfile`.

ده فصل مسؤوليات عملي: تغيير تنسيق زر ما يغيرش الطلب، وتغيير اسم حقل من الباك يتصلح في mapper، وتغيير مصدر البيانات يتم خلف repository. المشروع لا ينشئ interface لكل عنصر صغير؛ الفصل مستخدم حيث يفيد قابلية التعديل.

## 6. Dependency Injection: الاعتمادات بتيجي منين؟

نقطة تركيب الخدمات موجودة في `front/src/app/services.ts`. `createAppServices` يجهز الخدمات المستخدمة في الصفحات، و`createApiServices` يركب مدير الجلسة وعميل HTTP وتدفق OAuth ومستودعات الحساب والمصادقة.

`ServicesProvider` في `front/src/app/providers/services-provider.tsx` يوزع الخدمات عبر React Context. أي صفحة تستدعي `useServices()` فتلاقي العمليات الجاهزة، بدل ما تعمل `new HttpAuthRepository` أو تكتب عنوان السيرفر داخل المكون.

ده اسمه Dependency Injection: العملية بتستقبل اعتمادها من الخارج بدل إنشائه بداخلها. مثلًا repository يستقبل `HttpClient` و`BrowserSessionPort` و`OAuthFlowPort` في constructor. الاختيار بيحصل في composition root، مش في صفحة الدخول.

المشروع بدأ بواجهة يمكن عرضها وتجربتها من غير API، ولذلك توجد بقايا adapters تجريبية قديمة في المصدر. التشغيل الحالي يركب مستودعات HTTP فقط؛ وجود `DemoAuthRepository` في الملفات لا يعني إن المستخدم الحالي يتعامل مع حسابات وهمية.

## 7. DTO وModel وMapper: الفرق بينهم

DTO هو شكل البيانات عند عبور حد بين طبقتين. `SignInInput` يمثل بريدًا وكلمة مرور، بينما `BrowserSessionDto` يمثل رد الباك الخاص بالجلسة. `UserProfile` هو نموذج الحساب اللي صفحات React تتعامل معاه بعد التحويل.

وجود mapper يعزل فرق التسمية بين API والواجهة. في تعديل الحساب مثلًا الواجهة تستخدم `phoneNumber`، لكن `HttpAccountRepository.updateProfile` يحوله إلى `phone` في جسم طلب `PATCH /users/me`.

التحويل موجود في `features/account/infrastructure/mappers/user-profile-mapper.ts` و`address-mapper.ts`. الصفحات ما تحتاجش تعرف كل تفاصيل أسماء حقول الباك، وده يقلل تكرار التحويل وأخطاء عرض قيم ناقصة.

`UserProfile` يحتوي المعرف والاسم والبريد والهاتف وحالة تأكيد البريد واكتمال الملف والعنوان الافتراضي والأدوار. وجود `roles` يفيد العرض والتنقل، لكنه لا يمنح صلاحية على السيرفر بمجرد وجود قيمة داخل المتصفح.

## 8. بداية تشغيل الواجهة والمسارات

`front/index.html` يحدد لغة الصفحة واتجاهها، و`front/src/main.tsx` يستورد الخط وCSS ويشغل bootstrap ثم ينشئ React root. `App` في `front/src/app/app.tsx` يركب ErrorBoundary ومزودي الخدمات والإشعارات والـrouter.

`front/src/app/router/app-router.tsx` يجمع المسارات. مسارات الحساب تشمل `/login` و`/register` و`/verify-email` و`/forgot-password` و`/reset-password`، وبعد الدخول تظهر مسارات استكمال البيانات و`/account` والعناوين.

`RouteEffects` يحدث عنوان تبويب المتصفح، ويرجع التمرير لأعلى، ويحاول نقل التركيز لعنوان الصفحة. النتيجة إن الانتقال داخل التطبيق له عنوان واضح، ومستخدم الكيبورد أو قارئ الشاشة يقدر يلاحظ تغير الصفحة.

مع إضافة Sprint 2 اتوسع نفس router بمسارات المتاجر والسلة والطلبات والدفع. فصل الحساب لسه موجود، والمسارات الجديدة تعيد استخدام الجلسة والـguards بدل إنشاء تسجيل دخول مستقل للتسوق.

## 9. صفحة إنشاء الحساب: من الحقول لرسالة التأكيد

`RegisterPage` موجودة في `features/auth/presentation/pages/register-page.tsx`. تحتوي الاسم والبريد وكلمة المرور، وأزرار Google وFacebook، ورابط الرجوع للدخول. القيم محفوظة في state محلية طول ما المستخدم داخل النموذج.

`handleSubmit` يمنع إرسال HTML التقليدي، ويشغل `services.auth.signUp` من خلال `useAction`. الـuse case ينظف الاسم والبريد ويتحقق من كلمة المرور، ثم `HttpAuthRepository.signUp` يرسل `POST /auth/register`.

جسم الطلب يحتوي `name` و`email` و`password`. نجاح الطلب لا يعني تسجيل الدخول تلقائيًا في خطوة التسجيل؛ الصفحة تنتقل إلى `/verify-email` ومعها البريد لعرض تعليمات الخطوة التالية وإتاحة إعادة إرسال الرسالة.

الدومين الحالي يقبل كلمة مرور جديدة من 15 إلى 128 حرفًا. الصفحة تعرض الحد قبل الإرسال برسالة عربية. استخدام جملة طويلة يسهل تذكرها مدعوم؛ الفرونت لا يخزن كلمة المرور ولا يسجلها في storage.

## 10. تأكيد البريد والروابط اللي جاية من الإيميل

`VerifyEmailPage` تعرض تعليمات مراجعة البريد وإعادة إرسال رسالة التأكيد. عملية resend تمر على `services.auth.resendVerification` وتنتهي بطلب `POST /auth/resend-verification`؛ نص الاستجابة لا يستخدم لعرض بيانات حساب حساس.

رابط الإيميل يصل في صورة مثل `/verify-email#token=...`. قبل تشغيل React، `normalizeExternalLinks` في `app/bootstrap/external-links.ts` يحوله إلى المسار اللي `HashRouter` يفهمه. نفس الفكرة مستخدمة لإعادة ضبط كلمة المرور وعودة OAuth.

`useSensitiveSearchParam` يحتفظ بالقيمة المطلوبة داخل الصفحة ثم يزيلها من عنوان التنقل. ده يقلل استمرار عرض الـtoken في شريط العنوان، لكنه لا يلغي ضرورة صلاحية قصيرة واستخدام واحد والتحقق على الباك.

في إصلاح لاحق لتجربة الحساب، `ConfirmEmailPage` بقت تتطلب ضغط زر «تأكيد البريد ومتابعة بياناتي». الفتح وحده لا يستهلك الرمز، لتجنب استهلاكه بسبب أدوات معاينة الروابط أو فحص البريد.

النسخة الحالية تستدعي `POST /auth/browser/verify-email` وترجع `UserProfile` مع جلسة متصفح. بعدها الصفحة تحدث `SessionProvider` وتستخدم `accountDestination` عشان تنقل المستخدم لاستكمال بياناته. ده أصلح الرجوع غير المطلوب لشاشة الدخول بعد نجاح التأكيد.

## 11. تسجيل الدخول وتحديد الوجهة التالية

`LoginPage` في `features/auth/presentation/pages/login-page.tsx` تعرض البريد وكلمة المرور ورابط النسيان وأزرار OAuth. `handleSubmit` يمرر القيم إلى `services.auth.signIn`، و`HttpAuthRepository.signIn` يطلب `POST /auth/browser/login`.

عند النجاح، repository يقبل بيانات الجلسة ويحول المستخدم، ثم الصفحة تنادي `setUser(user)`. تحديد الصفحة التالية مش مكتوب في أكثر من مكان؛ الدالة `accountDestination` في `app/router/paths.ts` توحد القرار.

لو رقم الهاتف ناقص فالوجهة `/onboarding/profile`. لو الهاتف موجود والعنوان الافتراضي ناقص فالوجهة `/onboarding/address`. لو الاتنين موجودين فالوجهة `/account`. كده حساب Google الجديد والعميل المسجل بالبريد يكملان نفس الرحلة.

لو الباك رجع `email_not_verified` أو `email_verification_required`، صفحة الدخول توجه المستخدم لشاشة تعليمات تأكيد البريد. باقي الأخطاء تظهر برسائل مفهومة من خلال `AppError` و`FormError` بدل عرض stack trace.

## 12. نسيان كلمة المرور وإعادة ضبطها

`ForgotPasswordPage` تجمع البريد فقط، وتنفذ `services.auth.requestPasswordReset`. المستودع يرسل `POST /auth/forgot-password`، وبعد الاستجابة ينتقل المستخدم لشاشة `ResetPasswordSentPage` التي تشرح مراجعة البريد.

رابط الاسترجاع يصل إلى `/reset-password#token=...` ثم bootstrap يحوله إلى مسار React. `ResetPasswordPage` تجمع كلمة مرور جديدة وتأكيدها، والـuse case يتحقق من الرمز والكلمة قبل طلب `POST /auth/reset-password`.

بعد النجاح، `HttpAuthRepository.resetPassword` يمسح حالة الجلسة الموجودة في المتصفح، ويظهر مسار `ResetPasswordSuccessPage`. تغيير كلمة المرور لا يُعرض باعتباره تسجيل دخول جديد؛ المستخدم يرجع للدخول بكلمته الجديدة.

الفرونت لا يقرر صلاحية token أو انتهاءه ولا يفك تشفيره. عند رابط منتهي أو غير صحيح يعرض رسالة تطلب رابطًا جديدًا. مسؤولية المقارنة والتخزين والاستخدام الواحد وإبطال الجلسات المتعلقة بالحساب تقع على الباك.

## 13. تسجيل Google وFacebook: الواجهة بتعمل إيه؟

`SocialButtons` تعرض الأزرار، و`SocialSignInPage` تبدأ العملية. `BrowserOAuthFlow` في `features/auth/infrastructure/oauth-flow.ts` يتعامل مع الانتقال للمزود ثم استبدال نتيجة العودة بجلسة Foodify.

عند البداية يتم إنشاء `binding verifier` عشوائي باستخدام Web Crypto، وتخزينه مؤقتًا في `sessionStorage` باسم خاص بالمزود. نسخة challenge مشتقة منه تُرسل إلى `POST /auth/oauth/{provider}/start` عشان الباك يربط المحاولة بالتبويب الأصلي.

الباك يرجع `authorization_url`. الواجهة تتحقق من HTTPS والمضيف والمسار المتوقعين لـGoogle أو Facebook قبل `window.location.assign`، فتمنع استخدام رابط توجيه مجهول باعتباره بوابة دخول موثوقة.

بعد موافقة المستخدم، المزود يرجع للباك، والباك يرجع Ticket قصيرًا للواجهة. `OAuthCallbackPage` يستدعي `completeProviderSignIn`، و`BrowserOAuthFlow.complete` يرسل Ticket مع الـverifier إلى `/auth/browser/oauth/complete`.

عند النجاح تقبل الواجهة الجلسة، تمسح القيم المؤقتة، وتوجه الحساب إلى استكمال الهاتف والعنوان حسب `accountDestination`. كلمة مرور حساب Google أو Facebook لا تدخل Foodify، ومفاتيح المزود السرية لا تصل إلى React.

من الإصلاحات اللاحقة توحيد التشغيل المحلي على `127.0.0.1:5173` قبل إنشاء verifier؛ لأن `localhost` و`127.0.0.1` لهما storage منفصل. ده إصلاح لربط بداية OAuth بعودته، مع بقاء callback المسجل عند المزود مطابقًا لإعداد الباك.

## 14. استكمال الاسم والهاتف والعنوان

`CompleteProfilePage` تعرض الخطوة الأولى وتعيد استخدام `ProfileForm` الموجودة في `features/account/presentation/components/profile-form.tsx`. المستخدم يراجع الاسم ويضيف الهاتف، ثم `services.account.updateProfile` يحفظهما عبر `PATCH /users/me`.

`normalizeEgyptianPhone` في `account/domain/validation.ts` تقبل الصيغ المصرية المعتادة، وتحول الأرقام العربية والفارسية إلى أرقام ASCII. مثلًا الرقم المحلي يتحول لصيغة تبدأ بـ`+20`؛ التخزين الموحد يقلل اختلاف تمثيل نفس الرقم.

عند نجاح الحفظ، `ProfileForm` تحدث جلسة العرض بالمستخدم الجديد ثم تستدعي callback الصفحة. في onboarding يوجه callback إلى `/onboarding/address`، وفي شاشة تعديل الملف يرجع المستخدم للوجهة المناسبة للحفظ.

`CompleteAddressPage` تعرض الخطوة الثانية وتستخدم `AddressForm`. النموذج يعرض اسم المستلم ورقمه، واسم المكان مثل البيت أو الشغل، والمدينة والمنطقة والشارع والعمارة، مع دور وشقة وتعليمات توصيل اختيارية.

الواجهة تسمح بتأجيل كتابة العنوان والذهاب للحساب، لكن رحلة checkout في Sprint 2 لها guard لا يسمح بإكمال الطلب من غير ملف مكتمل. حرية استعراض الحساب لا تعني السماح بطلب بدون بيانات توصيل مطلوبة.

## 15. إدارة العناوين بعد استكمال الحساب

`AddressesPage` تعرض قائمة العناوين، و`AddressEditorPage` تستخدم نفس النموذج للإضافة والتعديل. `saveAddress` يمر على التطبيع والتحقق ثم يستخدم `POST /users/me/addresses` للإضافة أو `PUT /users/me/addresses/{id}` للتعديل.

`HttpAccountRepository.listAddresses` يتأكد أن الرد قائمة، ثم يستخدم `toAddress` لتحويل كل عنصر. المستودع يحتفظ بإحداثيات العنوان المحفوظة في ذاكرة داخلية، لأن نموذج الواجهة الحالي لا يحررها؛ عند PUT يرجعها مع بقية البيانات بدل مسحها ضمنيًا.

حذف العنوان يمر على `removeAddress` وينتهي بطلب `DELETE`. تعيين عنوان افتراضي يمر على `makeAddressDefault` وينتهي بـ`PUT /users/me/default-address/{id}`. الـID وحده لا يكفي للسماح بالعملية؛ الباك يتحقق من ملكية العنوان.

من التحسينات الحالية إن نجاح حفظ العنوان لا يتحول لفشل كاذب لو فشلت قراءة الحساب التالية. النموذج يفرق بين نجاح الكتابة وفشل refresh، فيبلغ المستخدم إن العنوان اتحفظ بدل دعوته لإعادة POST وإنشاء نسخة مكررة.

## 16. الجلسة: فين الـtoken وإزاي المستخدم يفضل داخل؟

`BrowserSessionManager` في `front/src/infrastructure/http/browser-session.ts` يحتفظ بـAccess Token في ذاكرة التطبيق. Refresh Token يصل كـ`HttpOnly Cookie` يديرها الباك والمتصفح، وجافاسكريبت لا تحتاج قراءته مباشرة.

الطلبات التي تحتاج الحساب تأخذ `Authorization: Bearer ...` من عميل HTTP. طلبات المتصفح ترسل cookies باستخدام `credentials: include`، وعند تحديث الصفحة يمكن استرجاع جلسة جديدة عن طريق `/auth/browser/refresh` ثم تحميل المستخدم من `/users/me`.

النسخة الحالية لا تحفظ Access أو Refresh Token في `localStorage`. استخدام `sessionStorage` في OAuth مخصص للـbinding verifier المؤقت وليس لحفظ كلمة المرور أو Refresh Token.

عند الخروج، `signOut` يلغي حالة OAuth ويطلب `/auth/browser/logout`، ثم يمسح حالة الحساب عند النجاح. واجهة الدخول والخروج مرتبطة بإجابة السيرفر، وليست مجرد تغيير أيقونة المستخدم في الواجهة.

المراجعات اللاحقة أضافت حماية للتزامن: refresh متزامن يستخدم Promise واحدة، وrevision يمنع ردًا قديمًا من إلغاء دخول جديد أو إعادة جلسة بعد الخروج. `SessionProvider` يتجنب استعادة cookie قديمة أثناء تأكيد البريد أو تبادل OAuth اللذين ينشئان جلسة جديدة.

## 17. المسارات المحمية وحدود حمايتها

`RequireSession` ينتظر تحميل الجلسة ثم يسمح بالدخول أو يعيد المستخدم إلى `/login`. `GuestOnly` يمنع حسابًا مسجلًا من البقاء في صفحة الدخول ويرسله للوجهة المناسبة، بدل الدخول في رحلة تسجيل غير لازمة.

`RequirePhone` يحمي خطوة العنوان في onboarding، و`RequireCompleteProfile` يحمي خطوة اكتمال الحساب وcheckout لاحقًا. الـguards تنظم تجربة المستخدم، لكن إخفاء الصفحة أو الزر ليس وسيلة لمنع HTTP مباشر من مستخدم غير مصرح له.

الحماية الفعلية لكل مورد على الباك. تغيير `roles` أو `user` من أدوات المتصفح لا يعطي صلاحية إدارة ولا ملكية عنوان شخص آخر. الفرونت يعتمد على رد `401` أو `403` ويعرض الحالة المناسبة بدل محاولة تجاوزها.

## 18. التحقق والأخطاء وإمكانية الوصول

قواعد الحساب في `auth/domain/validation.ts` تنظف البريد والاسم وتتحقق من طول كلمة المرور والرمز. قواعد العنوان تتحقق من الحقول المطلوبة وحدود طولها ورمز الدولة. ده يساعد المستخدم بدري، والباك يكرر التحقق لأنه جهة الثقة.

`ApplicationError` يحدد `code` و`message` وأخطاء الحقول وstatus وrequest ID عند وجوده، و`AppError` يطبق العقد. `api-error.ts` يحول أخطاء HTTP لصيغة يفهمها العرض؛ رسالة الخطأ الداخلية لا تُعرض كما هي بشكل عشوائي.

`useAction` يدير `pending` والخطأ وأخطاء الحقول، ويمنع إرسالًا ثانيًا أثناء العملية نفسها. عند الخطأ يحاول التركيز على أول حقل غير صالح، ويتجنب تحديث state بعد خروج الصفحة. كل نموذج يعيد استخدام السلوك بدل نسخه.

`Field` يربط label بالحقل ويضيف `aria-invalid` و`aria-describedby` للرسائل. `PasswordField` يوفر زر إظهار وإخفاء له اسم عربي و`aria-pressed`. وجود نص مفهوم للخطأ وإمكانية التركيز بالكيبورد جزء من التنفيذ، وليس الاعتماد على اللون وحده.

`ToastProvider` يعرض تنبيهًا قصيرًا قابلًا للإغلاق، و`LoadingState` يوضح الانتظار، و`ErrorBoundary` يعرض واجهة استعادة عند خطأ render. حالات الانتظار والنجاح والفشل موجودة عشان المستخدم يعرف نتيجة الفعل ولا يعيد الضغط من غير داعي.

## 19. التشغيل والأمان والأداء

التشغيل من `front` باستخدام `npm ci` ثم `npm run dev`، والموقع المحلي على `http://127.0.0.1:5173`. إعداد `VITE_API_BASE_URL` يحدد أصل ومسار الـAPI المشترك. عند تعديل ملفات البيئة لازم إعادة تشغيل Vite، لأن الإعدادات تُقرأ عند التشغيل أو البناء.

`npm run typecheck` يفحص الأنواع، و`npm run build:production` يفحصها ويبني ملفات النشر. نجاح build يثبت قابلية تجميع المشروع، لكنه لا يثبت أن Google Console أو SMTP أو Paymob تم إعدادهم بشكل صحيح؛ دول يحتاجون فحص تكامل منفصلًا.

أي متغير يبدأ بـ`VITE_` متاح داخل حزمة المتصفح؛ لذلك لا يوضع فيه JWT secret أو OAuth client secret أو SMTP password. الواجهة تستخدم إعدادات عامة فقط، وملفات CSS والخطوط تُبنى مع سياسة CSP المناسبة للبيئة.

إعادة استخدام المكونات والاعتمادات يقلل التعقيد. تحديث state محليًا يحصل للجزء المتأثر، والخط محلي، والطلبات تمر من نقطة واحدة. في Sprint 2 أضيف تحميل كسول لصفحات الطلبات والدفع، وده امتداد لاحق لتحسين تحميل الموقع مع زيادة النطاق.

## 20. رحلة كاملة يمكن للتيم شرحها

نبدأ بعميل يفتح `/register`: يكتب الاسم والبريد وكلمة مرور جديدة، و`RegisterPage` تنادي use case ثم HTTP repository ثم API. بعد نجاح الطلب يراجع شاشة تأكيد البريد، ويفتح رابط الرسالة ويضغط تأكيد.

في السلوك الحالي ينتج التأكيد جلسة متصفح، فتحدث React المستخدم وينقله `accountDestination` لخطوة الهاتف. حفظ الهاتف يمر على التطبيع و`PATCH /users/me`، ثم يكتب العنوان، و`saveAddress` يرسله للباك الذي يحفظه ويرجع النسخة المعتمدة.

بعدها يستطيع فتح `/account` لتعديل الاسم والهاتف أو قائمة العناوين. لو أغلق الصفحة ورجع، مدير الجلسة يحاول الاستعادة من cookie. لو خرج ثم عاد، تظهر له صفحة الدخول ويبدأ مسار المصادقة من جديد.

اللي سلّمه نطاق Sprint 1 هو أساس حساب قابل لإعادة الاستخدام: نماذج موحدة، خدمات منفصلة، repository interfaces، إدارة جلسة، معالجة أخطاء، ومسارات onboarding. Sprint 2 استخدم نفس الحساب والعنوان والجلسة عشان يضيف المتاجر والسلال والطلب والدفع والتتبع، بدل بناء نظام حساب ثاني.
