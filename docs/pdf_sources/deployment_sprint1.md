# Sprint 1 — فريق Deployment

## 1. ما مسؤولية الفريق؟

هدف Deployment تحويل المشروع من ملفات تعمل على جهاز المطور إلى خدمات يمكن للمتصفح الوصول إليها، مع إعداد قواعد البيانات والأسرار والبريد والجلسات وروابط OAuth.
في Sprint 1 كان نطاق التطبيق حساب العميل وعناوينه: التسجيل والدخول والتأكيد واستعادة كلمة المرور واستكمال الملف. الدفع والكتالوج والطلبات توسعات Sprint 2.
هذا الفصل يشرح البنية الحالية المستخدمة لاستضافة نطاق الحساب، ويبين الملفات المسؤولة وخطوات الإصدار. لا يعني وجود أمر هنا أن نشرًا جديدًا نُفذ وقت إنشاء PDF.
تغيرت محاولات الاستضافة والبريد خلال التطوير؛ Render وBrevo كانا ضمن محاولات سابقة، بينما الإعداد المرجعي الحالي يوجه API إلى FastAPI Cloud والبريد إلى Mailjet.

## 2. توزيع الأجزاء على الخدمات

| الجزء | الأداة أو الخدمة | سبب الفصل |
| --- | --- | --- |
| واجهة المستخدم | React وVite على Vercel | تقديم ملفات HTML وCSS وJavaScript |
| منطق التطبيق | FastAPI على FastAPI Cloud | تنفيذ API والتحقق والأعمال والجلسات |
| البيانات الدائمة | MySQL على Aiven | حفظ الحسابات والعناوين والأدوار والجلسات |
| الحماية من كثرة الطلبات | Valkey على Aiven | عدادات rate limiting المشتركة |
| رسائل الحساب | Mailjet عبر SMTP | توصيل رسائل التأكيد والاسترجاع |
| الكود والمراجعات | GitHub | حفظ الإصدارات وتشغيل CI |
| تجربة التطوير | Docker Compose وMailpit | بيئة محلية قابلة لإعادة التشغيل |

الواجهة المنشورة مرجعها `foodify-flax.vercel.app`، والـAPI مرجعها `foodify-api.fastapicloud.dev` كما هو موثق في إعداد المشروع.
لا يتصل المتصفح بـMySQL ولا يعرف كلمة مرورها. يرسل طلب API، والباك وحده يتصل بقاعدة البيانات باستخدام حساب مخصص.
Valkey ليست بديلًا عن MySQL، وليست المكان الذي تُحفظ فيه حسابات العميل. دورها هنا عدادات تحديد معدل الطلبات، مثل منع محاولات دخول أو طلبات بريد كثيرة.

## 3. الطريق الكامل في الإنتاج

```text
Browser → React على Vercel → /api/v1/* على نطاق Vercel
  → api/proxy.mjs → FastAPI Cloud
      → Aiven MySQL عبر TLS
      → Aiven Valkey عبر TLS
      → Email Outbox Worker → Mailjet SMTP عبر STARTTLS
```

عند الضغط على تسجيل الدخول، يطلب المتصفح `/api/v1/auth/browser/login` من نطاق الواجهة نفسه. يعيد Vercel توجيه هذا المسار إلى `api/proxy.mjs`.
الوسيط يمرر الطلب إلى النطاق المحدد في `FOODIFY_API_ORIGIN`، ويعيد استجابة الباك و`Set-Cookie` إلى المتصفح.
الـproxy لا ينفذ قواعد تسجيل الدخول ولا يحفظ حسابًا جديدًا. هذه مسؤولية FastAPI وخدماته ومستودعات MySQL.
تمرير طلبات المتصفح من نفس النطاق يساعد refresh cookie على العمل دون الاعتماد على cookies طرف ثالث بين Vercel وFastAPI Cloud.
عند OAuth، يرجع المزود إلى callback على API أولًا، ثم يعيد الباك المستخدم إلى صفحة callback في الواجهة لتبادل ticket قصيرة العمر.

## 4. ملفات النشر: كل ملف يذهب إلى أين؟

`vercel.json` في جذر المشروع يحدد تثبيت حزم `front`، وتشغيل build، ونشر `front/dist`، وتمرير `/api/v1/*` إلى وظيفة proxy.
`api/proxy.mjs` يُنشر كوظيفة خادم في Vercel. المتغيرات السرية التي يستخدمها تبقى في بيئة الوظيفة ولا تدخل حزمة React.
`back/pyproject.toml` يحدد تطبيق FastAPI Cloud عند `app.hosted:app`. والملف `back/app/hosted.py` ينشئ التطبيق عبر `create_app()`.
`back/Dockerfile` يجهز صورة Python، ويثبت `requirements.lock.txt`، وينسخ التطبيق وmigrations وscripts، ثم يعمل بمستخدم غير root.
`back/compose.yaml` يجمع خدمات التطوير: API وemail-worker وMySQL وRedis وMailpit. هذا الملف مخصص للتطوير المحلي، وليس نشر Aiven أو Vercel.
`back/scripts/release.py` يجهز قاعدة البيانات بإصدار migrations الصحيح، ثم يضيف reference data مثل الأدوار والصلاحيات.
`.github/workflows/build.yml` يشغّل فحوص الفرونت والباك والتوثيق في CI عند push أو pull request إلى main. الاختبارات الواسعة فيه أضيفت أثناء المراجعة النهائية.

## 5. البيئات الثلاث ولماذا فُصلت

| البيئة | استخدامها | أمثلة الإعداد |
| --- | --- | --- |
| Development | تطوير وتجربة محلية | React على 5173 وAPI على 8000 وMailpit |
| Test | اختبارات معزولة وحتمية | إعدادات اختبار دون أسرار الإنتاج |
| Production | تقديم الخدمة المنشورة | HTTPS وأسرار خادم وMySQL وValkey خارجيان |

يقرأ الباك `APP_ENV` ويحمّل إعدادات البيئة من `app/core/config.py`. يتيح `run.py` الاختيار الصريح عبر `--env development` أو `test` أو `production`.
وضع `--reload` مسموح في Development فقط، ويتطلب worker واحدًا. ذلك يمنع تشغيل إعادة التحميل التطويرية في الإنتاج بالخطأ.
يقرأ Vite وضع البناء من أوامره، مثل `build:production` و`build:test`. قيم `VITE_*` تُدمج في ملفات المتصفح وقت build، ولذلك تحتاج إعادة بناء إذا تغيرت.
لا يكفي تغيير ملف env على جهازك لتغيير موقع منشور. يجب تحديث بيئة الخدمة المعنية وإصدار نسخة جديدة وفق طريقة الاستضافة.

## 6. ما هو متغير عام وما هو secret؟

عنوان API العام واسم البيئة ليسا أسرارًا. يمكن للواجهة استخدام `VITE_API_BASE_URL=/api/v1` و`VITE_APP_ENV=production` و`VITE_DATA_SOURCE=api`.
أما `DATABASE_URL` و`REDIS_URL` و`JWT_SECRET` و`EMAIL_ENCRYPTION_KEY` وSMTP password وOAuth client secrets فتخص بيئة الباك.
يحتاج proxy إلى `FOODIFY_API_ORIGIN` و`FRONTEND_PROXY_SECRET`. يستخدم الباك القيمة المطابقة للسر للتحقق من ترويسات الوسيط الموثوق.
أي متغير يبدأ بـ`VITE_` يمكن أن يظهر في ملفات JavaScript التي يحملها الزائر. لذلك لا توضع فيه كلمة مرور أو secret حتى لو كان اسمه يوحي بغير ذلك.
ملفات `.env.*.example` قوالب بقيم توضيحية، بينما الملفات الفعلية ومجلد ربط `.fastapicloud` إعدادات محلية مستبعدة من Git.
لكل secret أثر محدد: تغيير JWT secret ينهي صلاحية الجلسات الحالية، وتغيير مفتاح تشفير البريد دون خطة قد يمنع فك رسائل outbox القديمة.

## 7. تجهيز قاعدة MySQL

تؤخذ بيانات host وport وdatabase وuser من خدمة Aiven، ثم يوضع الاتصال في صيغة SQLAlchemy مع driver PyMySQL.
الصيغة هي `mysql+pymysql://USER:PASSWORD@HOST:PORT/DATABASE?charset=utf8mb4`، مع ترميز الرموز الخاصة داخل بيانات الدخول وفق URL encoding.
استخدام `utf8mb4` يسمح بحفظ العربية والأسماء والرموز بشكل سليم. ولا يكفي أن يتصل MySQL client إذا كانت صيغة driver في إعداد التطبيق خاطئة.
تُفصل صلاحيات تشغيل API عن صلاحيات تعديل schema: الحساب العادي يقرأ ويكتب بيانات التطبيق، وحساب migration ينفذ تغييرات الجداول عند الإصدار.
تُستخدم `DATABASE_TLS_REQUIRED=true` وشهادة CA في `DATABASE_SSL_CA_PEM` أو المسار المحدد لها للتحقق من هوية خادم قاعدة البيانات.
ينشئ `app/infrastructure/database.py` سياق TLS يتحقق من الشهادة، ويشترط TLS 1.2 أو أحدث عند تفعيل التحقق.
تُضبط connection pool بما يناسب موارد الخدمة. إعداد المرجع الصغير يستخدم pool size يساوي 2 وmax overflow يساوي 1؛ التوسع قرار حسب الخدمة الفعلية.

## 8. تجهيز Valkey ومفهوم Fail Closed

يوضع رابط Valkey المشفر الذي يبدأ بـ`rediss://` في `REDIS_URL` داخل بيئة الباك. يحتوي الرابط على بيانات دخول، لذلك يعامل كسر.
عدادات rate limiting تحتاج مخزنًا مشتركًا؛ لو كان كل worker يحتفظ بالعدادات في ذاكرته فسوف تختلف حدود الطلبات بين النسخ.
في حالات الحماية التي تعتمد على Valkey، تعذر الاتصال لا يعني السماح بكل الطلبات. يستخدم التطبيق سلوك Fail Closed حتى لا تتحول مشكلة خدمة الحماية إلى تعطيلها.
هذه الحماية مستقلة عن JWT وملكية العنوان. اجتياز حد الطلبات لا يجعل المستخدم مصرحًا له بقراءة بيانات مستخدم آخر.
في Docker المحلي تؤدي خدمة Redis الدور المتوافق مع Valkey. بياناتها في volume منفصل عن بيانات MySQL.

## 9. تجهيز Mailjet ودورة البريد

يُضبط `EMAIL_PROVIDER=smtp`، والمضيف `in-v3.mailjet.com`، والمنفذ 587، مع `SMTP_USE_TLS=true` و`SMTP_USE_SSL=false` لاستخدام STARTTLS.
يستخدم إعداد Mailjet API Key كاسم مستخدم SMTP وSecret Key ككلمة المرور، ويجب توثيق عنوان المرسل أو نطاقه لدى المزود.
لا ترسل endpoint التسجيل رسالة SMTP داخل طلب المستخدم مباشرة. يحفظ الباك مهمة في جدول `EmailOutbox`، ويشفّر محتواها باستخدام `EMAIL_ENCRYPTION_KEY`.
العامل في `back/app/worker.py` يقرأ مهمة مستحقة، ويفك محتواها، ويتأكد من صلاحية الرمز، ثم يستخدم `create_email_sender()` لإرسال الرسالة.
بعد الإرسال أو انتهاء صلاحية الرسالة يمسح payload الحساس. وعند فشل قابل لإعادة المحاولة يزيد attempts ويؤجل next attempt تدريجيًا، بحد أقصى 10 محاولات.
هذا النمط يسمح بعودة `202` بسرعة، ثم متابعة البريد مستقلة عن اتصال طلب التسجيل. قبول التسجيل لا يعني أن البريد وصل إلى inbox بالفعل.
في Compose يعمل `email-worker` كخدمة مستقلة. وفي إعداد FastAPI Cloud الحالي يمكن استخدام `EMBEDDED_EMAIL_WORKER=true` لبدء العامل داخل دورة حياة التطبيق.

## 10. عنوان الواجهة وعنوان الباك: فرق مهم

`PUBLIC_BASE_URL` يحدد العنوان العام للـAPI، مثل `https://foodify-api.fastapicloud.dev`. ويُستخدم حيث يحتاج الباك إلى عنوانه الخارجي.
`FRONTEND_URL` يحدد عنوان صفحات المستخدم، مثل `https://foodify-flax.vercel.app`. يبني email sender منه روابط التأكيد والاسترجاع، ويعود إليه OAuth.
إذا بقي `FRONTEND_URL` على منفذ 3000، سوف تستمر رسائل جديدة في استخدام هذا المنفذ حتى لو كانت React تعمل على 5173.
ولأن worker هو الذي يبني رسائل البريد، يجب تحديث إعداداته وإعادة تشغيله مع API عند تغيير عنوان الواجهة. إعادة إنشاء API وحدها قد تترك العامل بالقيم القديمة.
الإعداد المحلي الحالي للواجهة يستخدم `http://127.0.0.1:5173`. توحيد هذا الأصل مهم لأن OAuth verifier محفوظ في sessionStorage المرتبطة بالأصل حرفيًا.
الرسائل القديمة لا تتعدل بعد إرسالها؛ بعد الإصلاح يجب طلب رسالة جديدة، وعدم الحكم على الإعداد الحالي من رابط قديم.

## 11. CORS والكوكيز وHTTPS

في التطوير يختلف Origin الواجهة عن API بسبب المنفذ. يضبط الباك `CORS_ORIGINS` بقائمة أصول محددة، وتستخدم الطلبات `credentials: include`.
`CORS` سياسة للمتصفح، وليست بديلًا عن authentication. وهي لا تمنع برنامجًا غير المتصفح من محاولة الاتصال بالـAPI.
تستخدم الجلسة access token قصير العمر في الذاكرة وrefresh cookie من نوع HttpOnly. يجب أن تتوافق SameSite وSecure والمسار مع البيئة الفعلية.
في الإنتاج يستخدم المشروع proxy من نفس نطاق الواجهة، مع `BROWSER_COOKIE_SAME_SITE=lax` كما توثق الإعدادات. يجب أن يمرر proxy كلًا من Cookie وSet-Cookie.
تحدد `TRUSTED_HOSTS` أسماء نطاقات API المقبولة. ولا تُفتح CORS أو trusted hosts إلى جميع الأصول لحل مشكلة إعداد محلية.
يضيف `vercel.json` ترويسات مثل `nosniff` و`DENY` و`no-referrer` وسياسة تمنع تأطير الموقع. وتضيف إعدادات Vite سياسة CSP متوافقة مع أصول الاتصال.

## 12. migrations والأدوار: إعداد قاعدة البيانات قبل API

إضافة ملفات Python إلى الاستضافة لا تنشئ الجداول المطلوبة تلقائيًا. لهذا يدير Alembic تغييرات schema بإصدارات محفوظة في `back/migrations`.
يقرأ `scripts.release` إعدادات البيئة، وينتظر جاهزية MySQL، ثم ينفذ Alembic upgrade إلى head، وبعده reference seed للأدوار والصلاحيات.
يستطيع script استخدام `MIGRATION_DATABASE_URL` لصلاحيات schema، ثم تستخدم بقية عمليات التطبيق حساب قاعدة البيانات المحدود.
لا يُشغَّل migration تلقائيًا مع كل بدء API؛ فصل خطوة الإصدار يمنع نسخًا متعددة من محاولة تعديل schema في التوقيت نفسه.
يجب مقارنة إصدار القاعدة بـ`alembic heads` الخاص بالنسخة المراد نشرها. لا تستخدم رقم migration مكتوبًا في شرح قديم بوصفه رأس كل الإصدارات المستقبلية.
Sprint 1 احتاج جداول الحسابات والأدوار والعناوين والجلسات ورموز البريد وoutbox. أما جداول الكتالوج والطلبات والدفع جاءت مع migrations Sprint 2.

## 13. ترتيب نشر أول نسخة

أولًا يراجع الفريق ملف البيئة ويجهز MySQL وValkey وبيانات TLS وحسابات الصلاحيات، ثم يتحقق من إمكانية الاتصال دون كشف الأسرار في السجلات.
ثانيًا يضبط عنوان المرسل وSMTP ومفتاح تشفير outbox، ويحدد عنوان الواجهة والباك النهائيين قبل إنشاء روابط المستخدمين.
ثالثًا يجهز بيئة إصدار آمنة، ويطبق `python -m scripts.release` باستخدام إعدادات البيئة المستهدفة، مع نسخة احتياطية مناسبة قبل تغيير بيانات قائمة.
رابعًا يربط مجلد `back` بتطبيق FastAPI Cloud القائم عبر CLI، ويضبط أسرار البيئة، ثم يستخدم `fastapi deploy` لنشر نسخة API المتوافقة مع القاعدة.
خامسًا يفحص `/health/live` و`/health/ready`. لا ينشر الواجهة التي تعتمد على endpoint جديد قبل أن تصبح API ومساراتها جاهزة.
سادسًا يضبط متغيرات Vercel، ويترك Root Directory عند جذر المستودع كي يجد `vercel.json` و`api/proxy.mjs`، ثم يبني وينشر الواجهة.
أخيرًا يراجع الرحلة من المتصفح: تسجيل، رسالة، تأكيد، استكمال هاتف وعنوان، reload واستعادة جلسة، وخروج. لا يكفي ظهور صفحة React لإعلان نجاح النظام كله.

## 14. إعداد Vercel بالتفصيل

`installCommand` هو `npm --prefix front ci`، وbuild الجذري يستدعي بناء الفرونت للإنتاج، وoutput هو `front/dist`.
قيمة `VITE_API_BASE_URL` الإنتاجية هي `/api/v1`. وقيمة `FOODIFY_API_ORIGIN` هي نطاق الباك فقط دون إضافة `/api/v1` إليه.
توجد rewrites لمسارات `/verify-email` و`/reset-password` و`/oauth/callback` إلى `/index.html` حتى تفتح روابط البريد وOAuth الفعلية صفحة React.
بعد تقديم index، يحول bootstrap fragment الخارجية إلى مسار HashRouter. هذه مسؤولية مختلفة عن rewrite الخاصة بالاستضافة.
يحدد rewrite آخر تحويل `/api/v1/:path*` إلى وظيفة proxy. تعالج الوظيفة forwarding وتوقيع عنوان العميل، وتمنع العميل من اختيار backend origin عشوائي.
رفع commit إلى فرع الإنتاج المتصل بـVercel يبدأ build وفق إعداد المشروع. نجاح push ليس إثباتًا لنجاح build؛ يجب متابعة نتيجة النشر نفسها.

## 15. إعداد Google وFacebook

كل مزود يحتاج Client ID وClient Secret وRedirect URI في بيئة الباك، وتسجيل callback المطابق في لوحة المطور لدى المزود.
مثال الإنتاج لـGoogle هو `https://foodify-api.fastapicloud.dev/api/v1/auth/oauth/google/callback`، ولـFacebook يتغير اسم المزود في المسار إلى `facebook`.
لا تضع callback في خانة سياسة الخصوصية أو شروط الخدمة؛ تلك الخانات تخص صفحات عامة تشرح سياسة التطبيق، وليست endpoints OAuth.
يتحقق مزود OAuth من تطابق URI، وقد يفرض أيضًا نطاقات معتمدة وحسابات اختبار أو نشر إعداداته. تطابق رابط الباك واللوحة ضروري لتجنب `redirect_uri_mismatch`.
بعد عودة المزود، يرجع الباك ticket إلى الواجهة. لا تحتاج الواجهة Client Secret، ولا يجب أن يصل إليها عبر VITE أو رابط callback.
بدء نافذة Google بنجاح يثبت بدء الرحلة فقط. الإكمال يحتاج حسابًا مسموحًا وإعدادات صحيحة وعودة callback ثم جلسة ناجحة واستكمال الملف.

## 16. التطوير المحلي وإعادة التشغيل

من مجلد `back` يستخدم الفريق `docker compose --env-file .env.development up -d --build` لبناء وتشغيل الخدمات المعرفة في Compose.
تعمل API على `127.0.0.1:8000`، وواجهة Mailpit على `127.0.0.1:8025`. وتعمل React بأمر `npm --prefix front run dev` على المنفذ 5173.
Mailpit يلتقط بريد التطوير ويعرضه محليًا؛ لا يعني ظهور الرسالة فيه أنها وصلت إلى Gmail حقيقي. يستخدم Compose المضيف `mailpit` والمنفذ 1025 داخل الشبكة الداخلية.
بعد تعديل إعدادات API وworker يمكن إعادة إنشائهما بـ`up -d --build --force-recreate --no-deps api email-worker` مع بقاء خدمات البيانات عاملة.
تحتفظ volumes المسماة ببيانات MySQL وRedis بين إعادة إنشاء الحاويات. إعادة بناء API لا تعني حذف البيانات، بينما حذف volume إجراء مختلف تمامًا.
تربط المنافذ المحلية على loopback فقط، وتعمل حاويات التطبيق مع `read_only` و`cap_drop: ALL` و`no-new-privileges`، وفق إعداد التطوير الحالي.

## 17. كيف يعرف الفريق أن النشر جاهز؟

`/health/live` يثبت أن عملية API تستجيب. أما `/health/ready` فيراجع MySQL وValkey وتوافق migration head، ويعيد `503` عندما لا تتوافر متطلبات الجاهزية.
لا يختبر health endpoint تسليم رسالة إلى صندوق بريد أو إكمال موافقة Google أو دفع بطاقة. كل تكامل خارجي له فحص رحلة مناسب.
في Network يتأكد الفريق أن طلبات الإنتاج تمر إلى `/api/v1` من نطاق Vercel، وأن login يعيد Set-Cookie وأن reload يستعيد الجلسة.
تُراجع مهام outbox والمحاولات وسجل مزود البريد دون طباعة payload أو tokens. وقد يقبل SMTP رسالة ثم تصنفها خدمة المستلم spam؛ لذلك يلزم التمييز بين الإرسال والتسليم.
يفحص الفريق السجلات بمعرف الطلب `request_id` وأكواد آمنة، ويمنع تسريب كلمات المرور أو authorization codes أو مفاتيح SMTP في السجلات والصور.

## 18. CI والتراجع وتسليم الشغل

CI الحالي يثبت الحزم ثم يشغّل اختبارات الفرونت والـproxy والعقود، واختبارات الباك، وبناء الفرونت، وتجميع Python، وبناء توثيق MkDocs.
هذه الفحوص أضيفت أو وُسعت أثناء مراجعة Sprint 2. لا توصف بأنها جزء مكتمل من أول تسليم Sprint 1، ولا بأنها تثبت سلامة كل خدمة منشورة.
قبل تحديث الإنتاج تُحفظ نسخة احتياطية وتُراجع قابلية migration للتوافق. إذا حدث خلل في واجهة أو API، يمكن الرجوع إلى إصدار كود متوافق مع schema القائمة.
لا تنفذ downgrade أعمى لقاعدة البيانات؛ فقد يحذف أعمدة أو بيانات. وإذا كان الخطأ إعدادًا، يصحح المتغير في الخدمة الصحيحة ثم يعاد نشرها.
يسلم الفريق قائمة الخدمات، وقيم الإعداد العامة، وأسماء الأسرار دون قيمها، وأوامر الإصدار، وفحوص الجاهزية، ومكان السجلات، وخطة الرجوع.
المرجع العملي لهذا النطاق هو `docs/DEPLOYMENT.md`. أما نشر migrations الكتالوج وPaymob وروابط callback للدفع وترتيب تحديث Sprint 2 فموضح في فصل Deployment الخاص بالسبرنت الثاني.
