# Sprint 1 — فريق Integration

## 1. هدف الفريق وحدود السبرنت

كان هدف Integration توصيل واجهة React بوظائف الحساب الموجودة في FastAPI: إنشاء الحساب، الدخول، تأكيد البريد، استعادة كلمة المرور، Google وFacebook، بيانات العميل، وعناوين التوصيل.
الربط هنا يعني الاتفاق على شكل الطلب والاستجابة، وإدارة الجلسة، وتحويل البيانات، ومعالجة الخطأ؛ وليس مجرد كتابة `fetch` عند الضغط على زر.
هذا الفصل يشرح نطاق الحساب الذي بدأ في Sprint 1 كما يعمل في المصدر الحالي. إصلاحات التأكيد وسباق الجلسة وتوحيد الأصل المحلي جاءت في مراجعات لاحقة، ومذكورة بوضوح في آخر الفصل.
الكتالوج والسلال والطلبات والدفع والتتبع ولوحة العمليات تخص Sprint 2، ولها فصل مستقل.

## 2. الأدوات ولماذا استُخدمت

| الأداة أو المفهوم | دوره في الربط | موضعه في المشروع |
| --- | --- | --- |
| TypeScript interfaces | تعريف عقود ثابتة بين الطبقات | ملفات `domain/*-repository.ts` |
| Fetch API | إرسال HTTP فعليًا إلى FastAPI | `infrastructure/http/fetch-client.ts` |
| DTO وMapper | عزل صيغة JSON عن نماذج العرض | مجلدات `infrastructure/dto` و`mappers` |
| React Context | إتاحة الخدمات والجلسة للمكونات | `app/providers` |
| Browser cookies | نقل refresh token دون قراءته من JavaScript | `BrowserSessionManager` والباك |
| Web Crypto | إنشاء وربط محاولة OAuth بالمتصفح | `auth/infrastructure/oauth-flow.ts` |
| OpenAPI وPostman | فهم عقود API وتجربة الطلبات | مخطط FastAPI ومجموعات Postman |

وجود هذه الطبقات يجعل تغيير عنوان السيرفر أو صيغة البيانات مسؤولية محددة. صفحة الدخول تظل مهتمة بالنموذج والتحميل ورسالة النجاح، ولا تتعامل مع تفاصيل cookie أو Authorization.

## 3. الطريق الذي يسلكه أي طلب

```text
React Page → Application Use Case → Repository Interface
  → HTTP Repository → FetchHttpClient → FastAPI
  → Response DTO → Mapper → Domain Model → React State
```

في البداية تجمع الصفحة المدخلات، مثل البريد وكلمة المرور. يراجع use case قواعد المدخلات الخاصة بالتطبيق، ثم يستدعي repository من خلال interface.
تنفيذ HTTP repository يختار endpoint ويجهز DTO. بعدها يرسل HTTP client الطلب مع الترويسات والـcookie المناسبة.
عند الرجوع، يحوّل mapper أسماء الحقول إلى نموذج الواجهة، ثم تعرض الصفحة النتيجة أو تنتقل إلى الشاشة التالية.
إذا فشل الطلب، ينتقل خطأ موحد `AppError` إلى العرض. لا تضطر كل صفحة إلى تفسير JSON مختلف أو معرفة أسرار الباك.

## 4. Dependency Injection: أين رُكّبت الأجزاء؟

نقطة التجميع هي `front/src/app/services.ts`. الدالة `createAppServices()` تختار خدمات API، ثم تنشئ `BrowserSessionManager` و`FetchHttpClient`.
يُمرَّر client إلى `HttpAuthRepository` و`HttpAccountRepository`. كما يحصل `BrowserOAuthFlow` على client ودالة لاعتماد الجلسة التي يرجعها الباك.
يُغلَّف كل repository بـuse cases مثل `createSignIn` و`createSaveAddress`، وتتيح `ServicesProvider` الناتج إلى الصفحات.
الصفحة تستدعي `services.auth.signIn(input)`، ولا تنشئ repository بنفسها. بذلك تكون الاعتمادية من العرض نحو interface، بينما اختيار التنفيذ موجود في مكان واحد.
المصدر الحالي يختار HTTP adapters دائمًا. وجود ملفات demo قديمة للحساب لا يعني أن التشغيل يستبدل بيانات الباك ببيانات محلية عند الفشل.

## 5. DTO mapping: لماذا لم نستخدم JSON مباشرة؟

الباك يعيد أسماء مثل `email_verified` و`default_address_id` و`delivery_notes`، بينما الواجهة تستخدم `emailVerified` و`defaultAddressId` و`deliveryInstructions`.
تتولى `toUserProfile()` في `features/account/infrastructure/mappers/user-profile-mapper.ts` تحويل ملف المستخدم. وتتولى `toAddress()` و`toAddressWriteDto()` تحويل العناوين للقراءة والكتابة.
على سبيل المثال، يصل رقم الهاتف في `user.phone` ويصبح `UserProfile.phoneNumber`. ويصل `address.is_default` ويصبح `Address.isDefault`.
الأهمية العملية هي أن component العنوان لا يتغير إذا تغير اسم حقل في HTTP؛ يتغير mapper والعقد المرتبط به معًا.
حقول مثل `id` و`created_at` و`is_default` تخص استجابة السيرفر، ولا تُنسخ إلى DTO إضافة العنوان. الواجهة ترسل الحقول المسموح للعميل بتعديلها فقط.
الحقول الاختيارية الفارغة مثل الدور والشقة تتحول إلى `null`. وكلمة المرور لا تُقص مسافاتها ولا تُحفظ في التخزين المحلي.

## 6. عميل HTTP المشترك

`FetchHttpClient.request<T>()` في `front/src/infrastructure/http/fetch-client.ts` هو المدخل الموحد لطلبات الشبكة.
يضيف `Accept: application/json` و`X-Foodify-Client: web`. وعندما يوجد body يضيف `Content-Type: application/json` ويحوّل الجسم بـ`JSON.stringify`.
الطلبات المحمية تحصل على `Authorization: Bearer <access-token>` من مدير الجلسة. أما التسجيل والدخول وعمليات البريد فتستخدم `authenticated: false` لأنها تسبق الجلسة.
يستخدم client قيمة `credentials: include` حتى يرسل المتصفح refresh cookie، ويقبل `AbortSignal` لإلغاء طلب لم يعد العرض يحتاجه.
الدالة `readJson()` تتعامل مع جسم الاستجابة، بما فيه نجاح `204` الذي لا يحتوي JSON. أما الاستجابة غير الناجحة فتُمرَّر إلى `readApiError()`.
عنوان الخدمة يأتي من `VITE_API_BASE_URL`: في التطوير عنوان API محلي، وفي الإنتاج `/api/v1` عبر وسيط Vercel.

## 7. التسجيل وتأكيد البريد

نموذج التسجيل يرسل `name` و`email` و`password` إلى use case، ثم `HttpAuthRepository.signUp()` يرسل `POST /auth/register`.
لا يرسل النموذج `confirmPassword`؛ فهذا حقل مقارنة محلي. ولا يرسل دور المستخدم، لأن صلاحيات إنشاء العميل يحددها الباك.
النتيجة `202` برسالة عامة، وليست access token. تنتقل الواجهة إلى شاشة مراجعة البريد، بينما يسجل الباك مهمة بريد في outbox ويرسلها worker.
عنوان الرسالة يتكون باستخدام `FRONTEND_URL` ويصل إلى مسار `/verify-email` ومعه token في fragment. هذا الرمز لا يظهر في طلب GET الذي يطلب الصفحة من الاستضافة.
تجهز `normalizeExternalLinks()` الرابط لكي يفهمه `HashRouter`، وتزيل الصفحة الرمز من شريط العنوان بعد التقاطه للاستخدام المؤقت.
يوجد ضغط صريح على زر التأكيد؛ فتح رابط البريد وحده لا يستهلك الرمز، حتى لا تستهلكه برامج فحص روابط البريد.
في النسخة الحالية يرسل `confirmEmail()` طلب `POST /auth/browser/verify-email`، ويستقبل جلسة وملف المستخدم، ثم يستدعي `session.accept()`.
هذا المسار الحالي يكمّل بيانات العميل مباشرة بعد التأكيد. أما `/auth/verify-email` القديم فيؤكد البريد ويعيد رسالة فقط، ولا يصدر جلسة متصفح.

## 8. الدخول: ما الذي ينتقل وما الذي يُحفظ؟

ترسل `HttpAuthRepository.signIn()` البريد وكلمة المرور إلى `POST /auth/browser/login`. الباك يتحقق منهما، ثم يرجع `access_token` و`expires_in` و`user`.
الـrefresh token يصدر في cookie باسم `foodify_refresh` مع `HttpOnly`. لا توجد قيمة refresh token ضمن JSON الخاص بجلسة المتصفح.
يحفظ `BrowserSessionManager.accept()` access token في ذاكرة JavaScript، ويحوّل mapper ملف المستخدم إلى `UserProfile` تعرضه `SessionProvider`.
معنى الذاكرة أن إعادة تحميل الصفحة تمسح access token. لذلك تستعيد الواجهة الجلسة من refresh cookie، ولا تحتاج تخزين التوكن في `localStorage`.
لا تستطيع مكونات React قراءة cookie من نوع HttpOnly. المتصفح يرسلها تلقائيًا للعنوان المطابق، والباك هو الذي يتحقق منها ويجددها.

## 9. تجديد الجلسة ومنع تضارب الطلبات

عند بدء التطبيق، يطلب `getSession()` جلسة موجودة في الذاكرة أو يستخدم `restore()` لإرسال `POST /auth/browser/refresh`، ثم يقرأ `/users/me`.
إذا انتهت صلاحية access token وأعاد طلب محمي `401`، يحاول HTTP client تجديد الجلسة مرة واحدة ويعيد الطلب بالتوكن الجديد.
إذا رفضت الإعادة أيضًا، تُمسح الجلسة ويظهر للمستخدم مسار الدخول. لا توجد حلقة retry غير محدودة.
لو انتهى توكن واحد ووصلت عدة طلبات في اللحظة نفسها، تستخدم `refreshPromise` عملية refresh مشتركة. هذا يقلل الطلبات المتكررة ويمنع تدوير refresh token عدة مرات متعارضة.
يستخدم مدير الجلسة عداد `revision` حتى لا يكتب رد قديم فوق جلسة أحدث بعد login أو logout. ويمنع client إعادة طلب بدأ بحساب سابق تحت هوية حساب آخر.
خطأ شبكة أو `5xx` أثناء refresh يُعرض كتعذر اتصال؛ لا يُفسَّر تلقائيًا على أنه كلمة مرور خاطئة. أما `401` فيعني أن الجلسة لم تعد صالحة.
عند الخروج، ينتظر المدير refresh الجاري ثم يرسل `/auth/browser/logout`. إذا فشل الاتصال لا تدّعي الواجهة نجاح إلغاء جلسة السيرفر.

## 10. استكمال الاسم والهاتف والعنوان

بعد الدخول أو OAuth أو التأكيد، تحدد `accountDestination(user)` في `app/router/paths.ts` المكان التالي بناءً على بيانات الباك.
إذا كان `phoneNumber` غير موجود، تكون الوجهة `/onboarding/profile`. وإذا لم يوجد عنوان افتراضي، تكون `/onboarding/address`. وعند اكتمالهما تكون `/account`.
ترسل صفحة الملف `PATCH /users/me` عبر `updateProfile()`، ويحوّل repository حقل `phoneNumber` إلى `phone`.
يجب أن يصل الهاتف بصيغة E.164 مثل `+201012345678`، حتى لا تعتمد قاعدة البيانات على أكثر من شكل للرقم نفسه.
عند حفظ البيانات تستقبل الصفحة ملف المستخدم المحدث، وتحدّث session state. لذلك لا تقرر الشاشة من نجاح الضغط وحده أن الملف اكتمل.
`RequireSession` يحمي صفحات العميل، و`RequirePhone` يوجه لاستكمال الهاتف، و`RequireCompleteProfile` يطلب اكتمال الملف. هذه الحماية تحسن التنقل، بينما التحقق الأمني النهائي يظل في الباك.

## 11. إدارة عناوين التوصيل

`HttpAccountRepository.listAddresses()` يقرأ `GET /users/me/addresses` ويحوّل كل DTO إلى نموذج `Address`.
`saveAddress(input)` يضيف عبر `POST`. وعند وجود معرف يستخدم `PUT /users/me/addresses/{id}`، لأن العقد يستبدل العنوان كاملًا.
تحتفظ طبقة repository بالإحداثيات المحفوظة التي لا يعرضها النموذج، لكي لا يمسح تعديل اسم الشارع latitude وlongitude دون قصد.
حذف العنوان يتم بـ`DELETE`، واختيار الافتراضي بـ`PUT /users/me/default-address/{id}`. الأخير يعيد ملف المستخدم وليس مجرد عنوان.
لا يرسل العميل `user_id`. الباك يستنتج المالك من الجلسة، ويتحقق أن العنوان تابع له؛ معرفة UUID لا تمنح صلاحية التعديل.
أول عنوان يصبح افتراضيًا تلقائيًا. وعند حذف الافتراضي يختار الباك أقدم عنوان متبق. لذلك تُحدَّث قائمة العناوين وملف المستخدم بعد هذه العمليات.
حد العناوين الحالي 20. وعند الوصول إليه تعرض الواجهة رسالة واضحة بدل فقد بيانات النموذج أو إظهار خطأ HTTP خام.

## 12. استعادة كلمة المرور

ترسل `requestPasswordReset()` البريد إلى `POST /auth/forgot-password`. تعرض الصفحة رسالة عامة حتى لا تكشف هل هذا البريد مسجل أم لا.
عند فتح رسالة الاسترجاع، يحول bootstrap المسار `/reset-password#token=...` إلى مسار التطبيق، ثم يحتفظ النموذج بالرمز مؤقتًا بعد تنظيف العنوان.
ترسل `resetPassword()` الرمز وكلمة المرور الجديدة إلى `POST /auth/reset-password`. لا ترسل حقل التأكيد الإضافي ولا كلمة المرور القديمة.
بعد النجاح يمسح repository الجلسة المحلية، ويطلب التطبيق دخولًا جديدًا. الباك يلغي الجلسات السابقة المرتبطة بالحساب عند استرجاع كلمة المرور.
لذلك يختلف هذا التدفق عن تأكيد البريد: التأكيد الحالي يصدر جلسة لاستكمال الملف، بينما reset password ينهي الجلسات ويعود إلى تسجيل الدخول.

## 13. تسجيل Google وFacebook خطوة بخطوة

الدالة `BrowserOAuthFlow.start(provider)` تنشئ 32 بايت عشوائيًا باستخدام `crypto.getRandomValues`، وتحولها إلى `binding_verifier` بصيغة URL-safe.
تحسب `challengeFor()` قيمة SHA-256 وتضع verifier مؤقتًا في `sessionStorage` الخاص بالتبويب والمزود. لا توضع كلمة مرور Google ولا access token في هذا التخزين.
يرسل المتصفح `POST /auth/oauth/{provider}/start` ومعه `binding_challenge`، ويستقبل `authorization_url`.
تتحقق الواجهة أن الرابط HTTPS ويذهب إلى صفحة المزود المعروفة، ثم تستخدم `window.location.assign` للانتقال إلى Google أو Facebook.
المزود يعيد المستخدم إلى callback في FastAPI. الباك يتحقق من state وهوية المزود، ثم يعيد التوجيه إلى `FRONTEND_URL/oauth/callback#ticket=...`.
الـticket تذكرة قصيرة العمر ولمرة واحدة، وليست access token. صفحة callback تزيلها من العنوان ثم ترسلها مع verifier إلى `/auth/browser/oauth/complete`.
عند نجاح الإكمال تعتمد الواجهة الجلسة، وتحذف verifier، وتستخدم `accountDestination()` لطلب الهاتف والعنوان عند نقصهما.
إذا كان بريد المزود يطابق حسابًا قائمًا غير مربوط به، لا تربط الواجهة الحسابين من تلقاء نفسها. تتعامل مع `oauth_account_link_required` وتطلب طريقة الدخول الأصلية.

## 14. لماذا تهم Origin وروابط العودة؟

الـOrigin هو البروتوكول واسم المضيف والمنفذ معًا. لذلك `http://localhost:5173` و`http://127.0.0.1:5173` أصلان مختلفان رغم أنهما على الجهاز نفسه.
`sessionStorage` مرتبط بالأصل؛ إذا بدأت OAuth من الأول ورجعت إلى الثاني لن تجد الواجهة verifier الذي أنشأته، وقد تفشل محاولة الإكمال.
الإعداد المحلي الحالي يستخدم `http://127.0.0.1:5173`. تحوّل `redirectLocalDevelopmentOrigin()` عنوان localhost إلى هذا الأصل قبل بدء React والجلسة.
هذا التحويل محلي في وضع التطوير، ويحافظ على المسار وfragment. لا ينقل أسرار الجلسة بين المواقع، ولا يسمح للمستخدم باختيار وجهة تحويل إنتاجية.
عنوان callback المسجل في لوحة Google أو Facebook يجب أن يطابق قيمة الباك حرفيًا. عنوان الواجهة ليس بديلًا عن callback المزود الذي يستقبله FastAPI.

## 15. توحيد الأخطاء بين التيمين

يتفق الطرفان على envelope يحتوي `error.code` و`message` و`details` و`request_id`. يقرأ `readApiError()` هذا الشكل ويحوّله إلى `AppError`.
تعرض الواجهة رسالة عربية معروفة بحسب code. أما الأكواد غير المعروفة فتستخدم رسالة عامة، دون عرض traceback أو body خام صادر من خدمة خارجية.
أخطاء `422` تتحول إلى أخطاء حقول: تزال بادئة `body` أو `query`، ويحوّل `phone` إلى `phoneNumber` حتى تظهر الرسالة بجوار مدخل الهاتف.
عند `429` يقرأ التطبيق `Retry-After`، سواء كان ثواني أو تاريخًا، ويحتفظ به في `retryAfterSeconds`. لا يعيد إرسال رسائل البريد آليًا في حلقة.
يبقى `requestId` متاحًا لمتابعة المشكلة في السجلات. هذا المعرف لا يمنح المستخدم تفاصيل حساسة لكنه يساعد الفريق على إيجاد الطلب الصحيح.

## 16. مثال كامل يمكن شرحه في العرض

عميل يفتح الموقع ويسجل اسمه وبريده وكلمة مروره. الصفحة تستدعي use case، ثم repository، ثم `POST /auth/register`، وتظهر شاشة «راجع بريدك» بعد `202`.
الباك يحفظ الحساب ورمز التأكيد ومهمة البريد. worker يرسل الرابط باستخدام عنوان الواجهة الصحيح للبيئة، والعميل يفتحه ويضغط تأكيد.
طلب `/auth/browser/verify-email` يرجع access token ومستخدمًا، ويصدر refresh cookie. تعتمد الواجهة الجلسة وتجد أن الهاتف والعنوان ناقصان.
يحفظ العميل الهاتف عبر `PATCH /users/me`، ثم عنوان المنزل عبر `POST /users/me/addresses`. يعود ملفه بعنوان افتراضي فتكتمل خطوة onboarding.
عند إعادة تحميل الصفحة تُستعاد الجلسة من cookie. وعند انتهاء access token يجدده client مرة واحدة ثم يعيد طلب الملف تلقائيًا.
كل خطوة لها مسؤول واضح: React للعرض، use case للتنسيق والتحقق، adapter للعقد، FastAPI لقواعد العمل، MySQL للحفظ، والـworker لتوصيل البريد.

## 17. ما الذي أُصلح لاحقًا في نطاق الحساب؟

كانت رحلة تأكيد البريد القديمة تؤكد الحساب ثم تطلب login من جديد. أُضيف browser verification endpoint في مراجعة لاحقة ليصدر الجلسة ويكمل بيانات العميل مباشرة.
أُوقف refresh التلقائي عند بدء صفحات OAuth callback وتأكيد البريد؛ لأن هذه الصفحات بصدد إصدار جلسة جديدة، ورد استعادة متأخر قد يتعارض معها.
أُضيف توحيد الأصل المحلي لمعالجة فقد verifier بين localhost و127.0.0.1. هذه إصلاحات للرحلة الأصلية، ولا يصح عرضها كأنها كانت موجودة منذ أول تسليم Sprint 1.
عندما يتغير `FRONTEND_URL` يجب إعادة إنشاء API وemail-worker وطلب رسالة جديدة؛ الرسائل القديمة تحتفظ بالروابط التي أُرسلت بها.

## 18. ما الذي سلّمه Integration لباقي الفرق؟

سلّم للفرونت interfaces ونماذج Domain ثابتة، وجلسة مركزية، ورسائل خطأ موحدة. وسلّم للباك requests تطابق DTOs، وهاتفًا بصيغة واضحة، ومعرفات موارد دون `user_id` قابل للتلاعب.
وسلّم للـDeployment قائمة origins وcallback paths وcookies وrewrites والمتغيرات العامة والأسرار. وسلّم للاختبارات حالات النجاح والفشل وانتهاء الجلسة وتغير الحساب والروابط المنتهية.
المرجع التفصيلي في المصدر هو `front/docs/INTEGRATION.md`، وعقود الباك في `back/app/users/**/dto.py` وOpenAPI. اختبارات الربط المضافة أثناء المراجعة النهائية موضحة في فصل فريق الاختبارات، ولا تعني اختبار مزودي OAuth الحقيقيين تلقائيًا.

## 19. كيف يشرح عضو الفريق الفرق بين الأخطاء؟

لو وصل `422` عند إضافة عنوان، فالطلب وصل إلى FastAPI لكنه خالف شكل DTO؛ يراجع الفريق اسم الحقل وصيغته ويعرض الرسالة بجواره.
لو ظهر خطأ CORS، يراجع أصل الواجهة وقائمة السماح وcredentials قبل تعديل منطق حفظ العنوان. هذه مشكلة عقد متصفح وإعداد، وليست دليلًا على تعطل MySQL.
لو فشل طلب بـ`401`، يراجع الفريق الجلسة والتجديد. ولو نجح login ثم فشل بعد reload، يراجع cookie والـproxy وOrigin بدل حفظ token دائمًا كحل سريع.
ولو عاد `503`، يراجع الجاهزية والاعتماديات والسجلات. هذا التقسيم يجعل كل تيم يعرف أين يبدأ البحث دون نقل المشكلة عشوائيًا بين الفرونت والباك.
