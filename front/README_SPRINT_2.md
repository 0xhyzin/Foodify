# Foodify Frontend — Sprint 2

شرح واجهات Marketplace وربطها مع الباك. التنفيذ React + TypeScript + Vite، بنفس الجلسة وطبقات الحساب الموجودة، وتصميم عربي RTL بأحمر/أبيض وأسود.

آخر مراجعة للكود والاختبارات: **2026-11-01**. هذا الملف يشرح الفرونت الخاص بالسبرينت الثاني، بما فيه إصلاحات التسجيل والتأكيد اللازمة لإكمال رحلة الطلب. شرح تفاصيل الربط في [INTEGRATION.md](docs/INTEGRATION.md)، ونتائج المراجعة النهائية في [SPRINT_2_VERIFICATION.md](../docs/SPRINT_2_VERIFICATION.md).

## تقسيم الملفات

كل الشغل الجديد في `src/features/marketplace/`:

- `domain`: models وواجهات Catalog/Cart/Order/Payment repositories. الأسعار strings؛ العرض عبر `Intl.NumberFormat`.
- `application`: use cases فيها validation الكمية وcheckout وفحص وجهة Paymob قبل الانتقال إليها.
- `infrastructure`: HTTP DTOs/mappers وclass مستقلة لكل repository؛ جميع بيانات المتجر والسلة والطلب تقرأ من API.
- `presentation/components`: مكونات العرض القابلة لإعادة الاستخدام، بدل جمع الواجهة في ملف واحد.
- `presentation/pages`: ربط المكونات لكل صفحة.
- `presentation/hooks`: تحميل بيانات قابل للإلغاء، وpolling للطلب أثناء ظهور التبويب.
- `marketplace-provider.tsx`: سلال ومفضلة الحساب الحالي، وحماية العرض من نتائج requests خاصة بحساب قديم.
- `marketplace-layout.tsx`: header والتنقل وسلالي والحساب والـfooter.
- `app/services.ts`: composition root يختار implementations ويحقنها. المكونات لا تحتوي fetch مباشرًا.

```text
src/
├── app/                              تهيئة التطبيق والـRouter والـProviders
├── features/
│   ├── auth/                         تسجيل الحساب والدخول وOAuth والتأكيد
│   ├── account/                      الملف الشخصي والعناوين واستكمال البيانات
│   └── marketplace/
│       ├── domain/                   النماذج وواجهات الـRepositories
│       ├── application/              عمليات checkout والكميات وبدء الدفع
│       ├── infrastructure/           DTOs وتحويل البيانات وتنفيذ HTTP
│       └── presentation/             الصفحات والمكونات والـhooks والتنسيقات
├── infrastructure/http/              HTTP client وإدارة جلسة المتصفح
└── shared/                           عناصر العرض والأخطاء والـhooks المشتركة
tests/frontend-regressions.test.mjs    اختبارات سلوك وأمان من دون اتصال بالخدمات
```

الصفحة تطلب عملية من خدمة محقونة، والخدمة تتعامل مع interface، وتنفيذ HTTP يحول النتيجة القادمة من الباك إلى نموذج مناسب للواجهة. مثلًا `CheckoutPage` تستخدم `createCheckout` ثم `OrderRepository`، بينما `HttpOrderRepository` هو الذي يعرف أسماء حقول API. بهذه الطريقة يمكن تغيير طريقة الاتصال من غير نقل تفاصيل HTTP إلى الأزرار والمكونات.

المجلدات القديمة `features/catalog` وبعض `demo-*` ما زالت ضمن المصدر من مرحلة العرض السابقة، لكنها ليست مصدر بيانات النسخة الحالية. `createAppServices()` يختار تنفيذ API فقط، وإعداد البناء يرفض `VITE_DATA_SOURCE=demo`.

## الربط بالـAPI

الـHTTP repositories تستخدم `FetchHttpClient` الحالي؛ يضيف Bearer token و`X-Foodify-Client`، ويتعامل مع تجديد الجلسة والأخطاء بنفس آلية الحساب. أضيف دعم `Idempotency-Key` إلى RequestOptions.

- تحميل الكتالوج/المنيو عام، أما السلال والمفضلة والطلبات فتابعة للحساب.
- add/update/remove/clear كلها ترسل `restaurant_id` في مسار السلة.
- المبلغ النهائي من السيرفر. checkout يرسل الإجمالي الذي راجعه المستخدم ونسخة السلة، والسيرفر يرفض أي تغيير قبل التحصيل.
- مفتاح checkout يعاد استخدامه عند إعادة نفس المحاولة؛ لا يولد مفتاحًا جديدًا بعد timeout بلا سبب.
- عند الدفع بالبطاقة/المحفظة، React ينتقل لرابط Paymob HTTPS معتمد بعد حفظ الطلب. لا توجد حقول PAN/CVV/OTP داخل Foodify.
- الرجوع من Paymob لا يجعل الطلب paid. صفحة الطلب تقرأ الحالة من الباك دوريًا.
- InstaPay يظهر بيانات المستلم المحفوظة مع الطلب، ويقدم العميل reference للمراجعة فقط.
- السلال الأخرى لا تُمسح بعد checkout أو تأكيد دفع متجر واحد.
- لا تتم إضافة provider secrets أو access/refresh tokens إلى localStorage.

## رحلة المستخدم من المتجر للطلب

1. الصفحة الرئيسية تطلب المتاجر والفئات من API. البحث والفئة والترتيب وفلاتر التوصيل تتحول إلى query parameters؛ الواجهة تعرض النتيجة القادمة من السيرفر.
2. فتح متجر يطلب تفاصيله ومنتجاته بالتوازي. الصور والشعارات والأسعار واسم المنتج تأتي من البيانات المخزنة في MySQL عبر FastAPI.
3. زر إضافة يرسل هوية المتجر والمنتج والكمية. تعديل كمية أو حذف بند أو إفراغ سلة يؤثر في سلة هذا المتجر. الانتقال إلى متجر آخر يحافظ على السلة الأولى.
4. صفحة «سلالي» تعرض كل سلال الحساب. المستخدم يفتح checkout لمتجر واحد؛ إذا كانت بيانات الحساب ناقصة، يمر أولًا باستكمال الهاتف والعنوان.
5. checkout يحمل السلة والمتجر والعناوين وطرق الدفع بالتوازي. المستخدم يختار عنوانه ووسيلة الدفع ويراجع المبلغ الظاهر.
6. إرسال الطلب يمرر `expected_total` و`cart_revision` مع `Idempotency-Key`. المفتاح محفوظ لنفس المحاولة في ذاكرة الصفحة و`sessionStorage` مع نطاق الحساب والمتجر؛ إعادة المحاولة بعد انقطاع الاتصال تستخدم المفتاح نفسه.
7. السيرفر هو الذي يقرر صحة السعر والمنتجات والعنوان ووسيلة الدفع. عند تغير السلة أو السعر تظهر رسالة للمستخدم ليحدّث البيانات قبل المحاولة التالية.
8. طلب الكاش ينتقل إلى صفحة الطلب. طلب البطاقة أو المحفظة يبدأ تجهيز Paymob، ثم ينتقل المستخدم إلى صفحة الدفع. InstaPay يعرض بيانات التحويل من الطلب إذا فعّله الباك.
9. صفحة الطلب تعرض البنود والعنوان والمبلغ ومرجع الطلب ومراحل التنفيذ. تحديث الحالة يتم بطلب API كل خمس ثوانٍ أثناء ظهور التبويب، ويتوقف عند التسليم أو رد التحصيل. توجد إمكانية طباعة الملخص من المتصفح.

## الدفع والحدود المهمة

| الوسيلة | تصرف الفرونت |
| --- | --- |
| البطاقة | يطلب رابط Paymob من الباك، يفحص الرابط وصلاحيته، ثم يفتح بوابة الدفع لكتابة بيانات البطاقة. |
| Vodafone Cash / Orange Cash | نفس رحلة Paymob باستخدام إعداد المحفظة الذي يختاره الباك. لا تجمع الواجهة OTP. |
| InstaPay | يعرض مستلم التحويل المحفوظ في الطلب، ثم يرسل العميل المرجع للمراجعة. كتابة المرجع لا تجعل الطلب مدفوعًا. |
| الكاش | يحفظ الطلب ويعرض أنه مستحق عند الاستلام. |
| simulated | يظهر فقط إذا أرجعه الباك كخيار مفعّل، ويوضح أنه تجربة من غير تحصيل. |

مصدر تفعيل أي وسيلة هو `/payments/methods`. وجود واجهة InstaPay أو المحفظة لا يعني أن حساب مزود الخدمة أو بيانات المستلم مكتملة. الوسيلة غير المفعلة تظهر غير متاحة.

`createStartPayment` يسمح فقط بـ`https://eg.checkout.paymob.com/` وبالمسار القديم المتوافق `https://accept.paymob.com/unifiedcheckout/`. يرفض المضيف المشابه، HTTP، المسار غير المعتمد، بيانات الدخول داخل الرابط، fragment، المعاملات الناقصة أو المكررة، والصلاحية المنتهية. لا تحفظ الواجهة رابط checkout أو أسرار مزود الدفع في تخزين دائم.

بعد حفظ الطلب، لو تعذر الانتقال التلقائي يظهر رابط واضح لاستكمال نفس عملية الدفع. لو رفض المزود تجهيز العملية تظهر الرسالة داخل صفحة الطلب مع بقاء الطلب محفوظًا. عند `initialization_unknown` لا يبدأ الفرونت عملية جديدة تلقائيًا؛ الحالة تحتاج مراجعة من الباك أو الدعم لتجنب ازدواج التحصيل.

صفحة الرجوع من Paymob تعرض حالة السيرفر، ولا تعتمد على `success=true` أو مبلغ موجود في عنوان المتصفح. تأكيد التحصيل مسؤولية callback يتحقق منه الباك. في التطوير المحلي، عنوان `127.0.0.1` لا يستقبل اتصال Paymob من الإنترنت؛ تأكيد الدفع الكامل يحتاج عنوان HTTPS متاحًا للمزود، مع إعداد callback الصحيح. الوصول إلى حقول البطاقة وحده لا يثبت نجاح التحصيل.

## تأكيد البريد وGoogle والجلسة

- رابط البريد الخارجي `/verify-email#token=...` يتحول قبل تشغيل React إلى صفحة HashRouter المناسبة. لا يستهلك الفرونت التوكن بمجرد عرض الصفحة؛ المستخدم يضغط «تأكيد البريد ومتابعة بياناتي».
- التأكيد يطلب `/auth/browser/verify-email`، ثم يحفظ access token في الذاكرة ويستقبل refresh cookie من الباك. ينتقل المستخدم مباشرة إلى استكمال الهاتف، ثم العنوان، أو حسابه إذا اكتملت البيانات.
- Google وFacebook يبدآن من الباك. الفرونت يحتفظ بقيمة verifier مؤقتة في `sessionStorage` داخل التبويب نفسه، ويتبادل تذكرة callback مع `/auth/browser/oauth/complete` قبل قبول الجلسة.
- لأن `localhost` و`127.0.0.1` لهما تخزين متصفح منفصل، يحول تشغيل التطوير `http://localhost:5173` إلى `http://127.0.0.1:5173` قبل إنشاء verifier. يحافظ التحويل على المسار والـquery والـfragment. لا يطبق هذا التحويل على الموقع المنشور.
- لا يبدأ `SessionProvider` استرجاع cookie قديمة عند فتح صفحة تبادل OAuth أو صفحة تأكيد البريد، حتى لا يتعارض الطلب القديم مع إنشاء الجلسة الجديدة.
- استرجاع الجلسة المتزامن يستخدم طلب refresh واحدًا. الاستجابة المتأخرة لا تمحو تسجيل دخول أحدث، ولا تعيد جلسة بعد الخروج. كذلك لا يعاد تنفيذ طلب فشل بحساب عميل آخر عند تغير الحساب أثناء الطلب.
- هوية OAuth لا تعوض بيانات التوصيل. `accountDestination` يرسل الحساب الذي ينقصه الهاتف إلى `/onboarding/profile`، والذي ينقصه عنوان افتراضي إلى `/onboarding/address`.

تسجيل الدخول الحقيقي عند Google/Facebook يحتاج إعداد Client ID/Secret وعنوان callback في لوحة المزود. الاختبارات المحلية تتحقق من كود الربط ومنع الروابط غير المسموحة؛ لا تدخل إلى حساب شخصي عند المزود ولا تثبت موافقته على إعدادات التطبيق الحالية.

## شاشة إدارة الطلبات

`OperationsPage` تعرض متاجر النظام وطلبات المتجر المحدد مع صفحات نتائج. `OperationalOrder` تعرض بيانات المستلم والبنود والحالة، وتسمح للفريق المخول بنقل الطلب إلى المرحلة التالية ومراجعة تحويل InstaPay.

ظهور الرابط في التنقل يتطلب دور `admin` أو `operations_manager`. هذا تحكم في العرض؛ الباك يتحقق من الصلاحيات لكل طلب API. تأكيد تحويل يدوي يتطلب مرجعًا وملاحظة وإقرارًا بمراجعة قيمة التحويل.

في المراجعة الأخيرة تم إصلاح احتساب المرحلة التالية: الحالات `cancelled` و`awaiting_payment` وأي حالة غير معروفة لم تعد تعرض زرًا يعيد الطلب إلى أول مراحل التنفيذ. `nextOrderStage` يسمح بالتقدم فقط داخل تسلسل `placed → preparing → ready → out_for_delivery → delivered`، والسيرفر يعيد التحقق من الانتقال.

## مصدر الكتالوج

مصدر بيانات المتاجر والفئات والمنتجات والأسعار وروابط الصور في التطبيق هو MySQL. `back/app/ordering/data/demo-catalog.json` ملف seed يستخدمه الباك إند فقط لمزامنة عينة من 8 متاجر مصرية و24 منتجًا؛ الواجهة لا تستورده ولا تستخدمه كبديل عند تعطل الاتصال. تمت مزامنة العينة إلى قاعدة التطوير وقاعدة الاستضافة بتاريخ 2026-10-31، وجرى التأكد من رجوعها من API بحالة 200.

`HttpCatalogRepository` يطلب القوائم من FastAPI، ثم يحول DTOs إلى نماذج المجال. صفحات React تعرض هذه النماذج فقط. إذا تعطل الاتصال تظهر حالة خطأ بدل استبدال بيانات قاعدة البيانات بداتا محلية. إعداد Vite يرفض أي قيمة غير `VITE_DATA_SOURCE=api`.

روابط الصور مخزنة في عمود `artwork` للمتجر والمنتج، وContent Security Policy تسمح بمضيفي الصور المحددين في الكود. الأسعار والأوقات والتقييمات بيانات عرض تجريبية؛ ليست مزامنة حية من الشركات.

## الواجهة والـUX

ألوان منضبطة بالأحمر/الأبيض والأسود، IBM Plex Sans Arabic، خطوط ومسافات وأزرار موحدة، RTL، وتدرج واضح بين اسم المتجر والسعر والإجراء. الهاتف له layout يتكيف من غير قص للمحتوى، والفئات والتنقل لها scroll أفقي عند الحاجة.

التحكم بالكيبورد، labels للـinputs وأزرار الأيقونات، focus ظاهر، skip link، حالات loading/empty/error، spinner أثناء الإرسال، reduced motion، وأسماء إجراءات مباشرة موجودة. الصفحات الثقيلة محملة بـlazy loading، والـrequests القديمة يتم إلغاؤها أو تجاهل نتائجها.

`useResource` يلغي الطلب عند مغادرة الصفحة أو تغير معايير التحميل. `MarketplaceProvider` يعزل السلال والمفضلة حسب الحساب، ويتجاهل نتائج الحساب السابق ويمنع استجابة قراءة قديمة من استبدال نتيجة تعديل أحدث. الأخطاء تظهر برسائل عربية من `AppError` بدل عرض تفاصيل داخلية للمستخدم.

البناء يضيف Content Security Policy، ويحمّل الخطوط من نفس الموقع، ويسمح بصور المضيفين المحددين فقط. React يعرض أسماء ووصف المنتجات كنصوص؛ لا يستخدم `dangerouslySetInnerHTML` لبيانات المتاجر. بيانات البطاقة وأسرار Paymob تبقى عند الباك أو بوابة الدفع.

## التشغيل

```bash
cd front
npm ci
npm run dev
```

للـAPI المحلي:

```text
VITE_DATA_SOURCE=api
VITE_API_BASE_URL=http://127.0.0.1:8000/api/v1
```

افتح `http://127.0.0.1:5173`. إعدادات `VITE_*` عامة وتدخل في ملف JavaScript الناتج؛ لا تضع فيها كلمة مرور أو مفاتيح Paymob أو مفاتيح OAuth السرية. في الإنتاج يستخدم الفرونت مسار `/api/v1` على نفس موقعه مع الـproxy المجهز في المشروع.

تشغيل اختبارات الفرونت وفحص النوع والبناء:

```bash
npm test
npm run typecheck
npm run build:test
npm run build:production
```

`npm test` يستخدم Node test runner وVite الموجود بالفعل لتحميل ملفات TypeScript والـaliases. لا يحتاج تثبيت test framework جديد، ولا يرسل رسائل بريد أو طلبات Paymob ولا يقرأ مفاتيح الدفع. ملف الاختبارات يحتوي بيانات صناعية ومضاعفات HTTP داخل الذاكرة.

قبل نشر الفرونت، يجب نشر الباك المتوافق، وتطبيق migration `20261031_0005`، ثم مزامنة الكتالوج إلى MySQL. ملف مفاتيح Paymob يخص الباك فقط. التفاصيل الكاملة في [README السبرنت](../back/README_SPRINT_2.md) و[شرح تدفق الكتالوج](docs/CATALOG.md).

الاختبارات تغطي السماح بروابط Paymob المعتمدة ورفض الروابط غير الآمنة والصلاحية المنتهية، تمرير فشل الدفع غير المؤكد دون تكرار، تطبيع روابط البريد وOAuth، توحيد عنوان التطوير، سباقات refresh/login/logout، منع إعادة الطلب بحساب مختلف، بدء الجلسة بعد تأكيد البريد، تبادل OAuth باستخدام verifier وحذف قيمته بعد الاستخدام، رفض وجهات OAuth غير المعتمدة، حدود الكميات، نطاق متجر السلة، تمرير بيانات checkout ومفتاح منع التكرار، ومنع إحياء الحالات الملغاة في واجهة العمليات.

هذه اختبارات منطق وربط HTTP باستخدام استجابات داخل الذاكرة. ليست E2E كاملة على متصفح مع MySQL أو حساب Google أو تحصيل بطاقة حقيقية. نتيجة أي فحص حي أو مراجعة متصفح، وإجمالي اختبارات المشروع والقيود البيئية، موثقة منفصلة في [SPRINT_2_VERIFICATION.md](../docs/SPRINT_2_VERIFICATION.md).
